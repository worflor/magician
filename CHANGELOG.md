# Changelog

Newest first. Dates are when the capability was proven, not when the code was written.

Each release's entry says whether the lint rules, the grading rubric or the built-in policy changed (`magician update --describe` shows the fingerprints), because that is what `magician update --check` tells a user to re-run `lint` and `grade` for. An entry that says nothing about them says they did not.

## Unreleased

- **Publishing to Nexus Mods.** `magician publish nexus <bundle.json>` (`tools/publish.py`, standard library) puts the zip `magician bundle --zip` wrote on a Nexus Mods page made on the site (a draft will do), through Nexus's v3 API as their own GitHub Action uses it: the multipart upload, then the page's first file (from the page's address, whose number is looked up as the page's id; the new file id is printed for `bundle.json`) or a new version of that file, with the bundle's `release`, name, description (cut at a word to 255 characters) and Nexus's switches, and the zip's changelog section for that release. `--page` also sets the page's summary and BBCode description from files beside the bundle; nothing else touches the page. The page and its file live in a `nexus` block in `bundle.json`; the key is `NEXUSMODS_API_KEY`, read from the environment only and never printed. Making the page, publishing it, and its generative-AI declaration (which Nexus requires of every page since 3 November 2026) stay on the site: the API has no call for them. Whether a draft page takes these calls is not known until the first real run. Before anything is sent the zip's own paks go through the release gate `grade --gate` holds (a proof of these bytes on the installed build, no file byte-identical to Valve's, rights, lint, fair play when enforced): a blocker refuses with exit 3, `--ignore-gate` overrides and says so. `--dry-run` says what would go where and sends nothing. A version already on the file is said, not uploaded again, and a page never gets a second file of the same name. Proven against a fake Nexus on this machine (`tools/test_publish.py`), not yet against the real one; [docs/reference/nexus-mods.md](docs/reference/nexus-mods.md). Lint rules, grading and policy: unchanged.
- **Magician asks the game whether its findings are true.** `magician witness <pak>... --log <console.log> [--vanilla <console.log>]` holds a mod's findings against an in-game pass: the engine's own lines (a resource that failed to load, an attachment looked up and missing, a camera pivot turned the wrong way, a camera pose it zeroed, a texture slot a material lacks, and with `snd_showstart 1` every sound file started) and a vanilla run of the same scenarios make each finding confirmed, contradicted, not reached (with the action that would reach it), a frame's or a file fact, and list the game's complaints no finding predicted. Every outcome is kept in `<reference>/<build>/witness.tsv`. `magician corpus` runs rules over Valve's own content, which works by definition, and keeps `<reference>/<build>/corpus.tsv`; `magician rules` prints both under each rule. The stock `witness` scenario is the probe (any hero: a scenario may name `{hero}` and the session fills it in). `session --pak` now takes a pak out of a slot that was free at `down`, and `--force` (with `--pak` and `--restore` only) looks at a pak lint refuses. `install --as` takes a pak whatever its file is called, as its refusal said. `cloth` says what a position-driven node is.
- **Judgement changed** (lint judgement revision 2; re-run `lint` and `check`). Evidence: seven published mods by another modder, each put in the game on 6868 and witnessed, and the corpus. M106 cut-body-void is a warning: nine openings it reported on a published model were not visible from the gameplay camera at any pitch or close behind the head; an opening is seen, not a model that fails. M071 is an error only when the shipped default's pixels differ from Valve's: every copy in three published mods decoded to Valve's own pixels or sat at a path Valve does not ship, which changes nothing. M063 does not judge a voice line (`sounds/vo/`) by its length (M064 neither): Valve's own voices fail that test against each other on 46% of the 79,572 pairs of lines two heroes share. M063 reads a changed sound-event base through the game's base events: a base Valve's inherits from differs only by what lies between, so `Base.Ability` for `Base.Ability.Cast` (one flag, no level or reach) is no finding and `Base.Movement.Melee` for `Hero.Default.Melee.Swing` (Valve's 2 dB quieter) is M064 louder. M001 is not said of a file the game never reads (M012). M033 does not report a material or texture the mod draws with (an exporter's `dummy` name on the real art). New: M149 material-texture-dropped (warning), a replaced material without a texture slot Valve's has: the game logged the missing slot and drew its error texture 50 times in one pass of a published mod, and no rule had said so. A candidate cloth rule (a loose chain lighter than the hero's fall rises when he is airborne, seen on a skin's headband ribbons) was measured on the corpus first and not written: it fires on 59 of Valve's 200 cloth groups. Grading rubric and policy: unchanged.

- **Mods made by someone else.** Published mods by other modders, taken through moving-to-magician as an agent with no other knowledge would, showed where a stranger's mod falls down; this is what changed. `init` takes downloads and paks from elsewhere: `magician init "Cool Skin.zip"` takes the paks out of the archive, and nothing else, into a new folder named for it (a zip is read here; a .7z or .rar goes through bsdtar, which Windows ships as `tar.exe`). Several paks and archives in one call make one mod, every copy is proven the same bytes and printed with its sha256, a pak whose every file another ships byte for byte is left out, and two paks that ship one path with different bytes are said. A bare `init` takes every pak in the folder, not only `pakNN_dir.vpk`. `magician diff <a.vpk> <b.vpk>` is the parity proof of a move or a rebuild: the same file, or each path only in one, the same bytes, recompiled (only the compiler's RED2 or REDI record differs) or different with the blocks that differ; exit 0, or 1 when something differs. `check` follows its lint line with the findings by rule (errors, warnings, fair play) and carries them as `by_rule` in its JSON; a lint of more than ten findings ends with the same tally; a grade's violation and advisory lines carry what was measured, and past five of one rule they are counted. A mod for no hero says what it is (a prop mod and the models it replaces, an effects or sound mod) in `init`, `check` and the not-graded label. M062 says when a changed attachment is Valve's with its axes in another order, the mark of an exporter's Y-up/Z-up swap. A bare `ls` in a mod's folder lists its paks; `grade` there on a mod for no hero says what it is instead of asking for `--hero`; `drift` filled in from a mod with no proof said `proven on` the build it fell back to, and now says `from` it. `init` names the files a mod ships of another hero than its own (`also   1 file(s) of hero_atlas (Abrams): ...`). `lint` prints a run of one rule on one file that differs only in a counting number as one line (`swing_long_01..25.vsnd_c' (25 findings)`) and an explanation a block's findings share once, marked `(*)`; its JSON keeps every finding. M062 also knows a turned attachment at the origin by its rotation, and shows only the influences an attachment has. M031 says when a voice line is one Valve records for other heroes and not for this one. `check` puts fair play's advisories (M081) on a row of their own, and a broken mod's `next` names only the list that holds what broke it. A grade's lines are cut at a word, not inside one. `refs`, `dump`, `mesh` and `cloth` take a path in a pak as its source (`models/x.vmdl`). Fixed: a hero whose core group holds another model that sorts before her own (Paige's effect model) had a replacement of her whole model graded as a Kit with no model; the grade reads the model heroes.vdata names. Fixed: Lady Geist's cards and portraits (`spectre_card`, named in her own heroes.vdata block) were not in her footprint, so a mod replacing them was credited with none of 0; a hero's own block names its art whatever it is called. Lint rules and policy: unchanged (three messages say more). Grading: those two mods are now graded for what they ship; re-run `grade`.

A full compile of Maid Lash's addon under Wine gave 550 of its 551 files byte for byte as Windows does, the body model differing only in a distance-field block the compiler does not repeat between runs. `grade`, `footprint` and `index` are proven on Linux with Source 2 Viewer 21.1's Linux CLI: the same grade record, footprint and users index as Windows. - **A command accepts only its own options.** `magician install --dry-run` installed: `--dry-run` belongs to `sign` and `update`, and the check let through any option some command took, so a guessed "do nothing" flag on a command that changes things got the change. Now an option the command does not take is a usage error (exit 2) before anything runs, and the message names the commands that do take it and the nearest option this one takes: ``--dry-run is not an option of `magician install` (`sign` and `update` take it)``. To make that safe, the usage text now says what the code reads: `--holder` and `--ignore-game` on `install` and `scene install` (they were documented only under `uninstall`), `--addon-root` and `--users` on `lint`, `--baseline` and `--users` on `grade`, `--force-compile`, `--lock-timeout` and `--baseline` on `release`, `--mod` and `--baseline` on `check`, `--out` on `index`, `--baseline` on `scan`, `--json-out` on `mesh`; `pack`, `build` and `install` take lint's options for the lint they run; the reference folder, `--no-cache`, the policy and the locations are declared once with the commands that take them, and `magician help <command>` lists every option that command takes. Every call the toolkit's tools and Magician itself make, and every command line in the docs, is held to this by a test. `release --bin` is refused as `build`'s option. Lint rules, grading and policy: unchanged.

- **The grade changed: it describes what a mod makes its own, and has no letter.** A letter made a mod that changes less read as a worse one. A label is now the kind of mod and the parts of the hero it makes its own: `Costume (look, effects, sound)`, `Echo (look, some effects) · NSFR · unproven`, `Kit (sound)`. The groups are look (model, materials, UI art, scenes), effects (ability VFX, animation) and sound (kit sound, and the voice once the mod treats it: an untouched voice reads `Valve's voice` in the facts and does not hold sound back); a group is named when the mod covers it, `some <group>` when it has begun it, and left out while it is Valve's. Under the label the report says what was counted, one line per group, in the game's terms (`look     model, materials, UI art 11 of 13, scenes 1 of 3`). Echolite is gone with the letters, and so are the caps: lint errors that are not fair play add the flag `broken`, the same word and the same test `check` uses, and a shipped skeleton, graph or data file or a dropped dependency is a note. Fair play (`NSFR`, `FP?`), freshness (`stale(N)`, `unproven`), identity, rights and the release gate are unchanged. On a terminal `broken` is red, `NSFR` pink, `FP?`, `stale` and `unproven` orange, a fair-play pass green. The record is `magician.grade/3`: `depth` (letter, score, caps) is replaced by `description` (kind, groups with state, coverage and what was counted, every criterion's measured coverage, notes) and `broken`. Grading rules 3.1.0: re-run `grade`. Policy: `[letters]` and `coverage.kit_departments` are gone (a `[letters]` section is refused with what replaced it), the weights count within a group and no longer total 100, and `[groups] covered` (0.8) and `touched` (0) are the lines that name a group. Animation and UI art are judged on what the hero has, so a hero with two ability clips is full at two. Old labels map like this:

  | Was | Now |
  |---|---|
  | `S Echo`, `A Echolite` ... `F Echolite` | `Echo (...)` with the groups it makes its own |
  | `S Costume` ... `F Costume` | `Costume (...)` |
  | `S Variant` ... `F Variant`, `S Kit` ... `F Kit` | `Variant (...)`, `Kit (...)` |
  | a letter capped at C by lint errors | the same description, then `· broken` |
  | a letter capped by a skeleton, graph or data file, or by dropped dependencies | the same description, and a note in the report |
  | Maid Lash, `S Costume` | `Costume (look, effects, sound)` |

- `magician update`: updating is easy, and finding out whether there is an update is too, and neither happens unless you run it. `update --check [--json]` reads the release's `VERSION` from the update source (`--source`, `MAGICIAN_UPDATE_SOURCE`, `update_source =`, else the latest release of the repository; a folder works as well as a URL) and says current, behind, ahead or unknown, and whether updating would change judgement (the grading rubric, the built-in policy, the lint rule set); exit 0 current or ahead, **5 an update is available** (a new exit code, used only here), 3 could not check. `update` applies it: a release install checks the archive's SHA-256, unpacks beside the toolkit, swaps the files in and rolls everything back if a step fails; a git checkout fast-forwards and runs `cargo build --release`, refusing local changes and putting the tree and the program back if the build fails. Both refuse while a game session holds the seat. `--dry-run` says what it would do, `update --describe` prints this build's own `VERSION`. `doctor` names the toolchain, and `doctor --updates` adds the check as a line (a source that can't be read is a note). Network steps are bounded to 10 s, and no other command goes online. `tools/make-release.ps1` writes a release (the asset for the platform, `VERSION`, `SHA256SUMS`) and `.github/workflows/release.yml` runs it for a `v*` tag on Windows and Linux; the workflow has not run on GitHub yet. Lint rules, grading and policy: unchanged.
- `magician reprove` joins the front door (`ingame/reprove.py`), and `reprove --json` prints its document alone on stdout with everything else on stderr.
- `patchday` and `reprove` find a folder of mods whatever it is called: the mods `--mod` names, else every mod under `MAGICIAN_MODS` (or `mods =` in the config file), else the nearest folder, from the working one upward, with `mod.toml` files one or two levels below it. They looked for a folder named `model-replacements` before. `magician paths` has a `mods` row.
- The docs were gone over as one piece: the README leads with one front door and a mod as a folder, the skill covers the in-game re-prove, starting a mod and publishing, the runbook's drills are history at its end, and the status page says what works and what is left, with no dated narration.
- `ingame/reprove.py`: patch day in game in one command. It runs the patch-day check (capturing a new build's baseline), then for each mod that needs a re-prove a vanilla pass when the build has no log for its hero and map, the mod's `[ingame] pass`, and the warnings it adds over vanilla, into `<reference>\work\passes\<slug>\`. One report gives each mod a state: `ready`, `look`, `failed` (exit 0, 4, 1). `--plan` launches nothing. `reprove.py accept <pass>` checks the pass is whole, on the installed build and of the installed paks, then runs `magician prove --evidence <pass>`. Written and run unattended on the 6866 to 6868 update the same day.
- Stills are not compared between passes. It was built and measured: two passes of the same pak differ in 3 to 13% of a still's grid cells (idle sway, neon, sky), a whole skin against vanilla in 3 to 17%. No threshold tells them apart; the numbers are in docs/PATCH-DAY.md.
- `mod_session.py --help` and `reprove.py --help` print the usage and exit 0.
- One front door. `magician session ...`, `magician bundle ...` and `magician source ...` run `ingame\mod_session.py`, `tools\bundle.py` and `tools\source.py` with the same arguments, stdio and exit code, so nobody has to know which part is Python. The toolkit folder is `MAGICIAN_HOME` (or `home =`), else the folder above the executable that holds `ingame\mod_session.py`; Python is `MAGICIAN_PYTHON` (or `python =`), else `python`, `python3` or `py -3`. When one is missing the verb says which and how to point at it (exit 2). `doctor` and `paths` show both, `magician help` lists the verbs, and every hint the CLI prints now uses them (`patchday`'s verdict and `check`'s next step say `magician session qa --mod <folder> --out <dir>`, then `magician prove --evidence <dir>`). `bundle.py --help` and `source.py --help` print their usage and exit 0.

- `magician new <hero> [--slug NAME] [--dir DIR] [--name NAME] [--author NAME]` starts a skin from nothing, where `init` needed a pak that already exists. From the installed game's hero table and the hero's compiled model it writes a mod folder in the shape the reference skins converged on: `mod.toml` (`[mod]` with the author or a marked blank, `[target]` the real model and the skeleton the model references, Viscous's being Kelvin's; `[proven]`, `[rights]` unreviewed, `[ingame]`), an `addon\` at the hero's compiled paths with the `.gitignore` files that keep Valve-derived files out of git and a `magician.allow`, a `package\` (`bundle.json`, `README.template.md`, `CHANGELOG.md`) that `tools/bundle.py` takes once a pak exists, `enter_<hero>.txt` and `<hero>_angles.txt` scenarios, and a README with the next commands. It copies no Valve file and never writes into a folder that exists (exit 3). `magician` in such a folder says "no pak yet" and leads with the `release` that builds one; `check` says the same instead of failing on a missing pak.

- `patchday` says whether a patch changed the engine or only the data. A build's baseline listed `pak01_dir.vpk` alone, so the 6865 to 6866 update, which replaced `engine2.dll`, `client.dll`, `server.dll` and `host.dll`, read "no drift". `baseline` and `patchday --capture` now also write `<build>\engine.tsv`: size and sha256 of every executable and library under `bin\win64` and `citadel\bin\win64`, every `shaders_*_dir.vpk`, and `gameinfo.gi` as shipped (the citadel one from the build's stock backup, or as it is when no install edited it; otherwise recorded as not known). Per era `patchday` prints `data only` or `engine too` with the files (`engine` in `--json`); it never changes a verdict. An era captured before has no record and is said so. `doctor` points out a missing one.

- A proof belongs to the bytes it was a proof of. `magician prove` used to append the installed build to `[proven] builds` and nothing else, so a rebuilt pak inherited every proof of the one before it: Maid Lash 1.0.1 (pak b43) read "proven on 6864, 6865 and 6866" on its store page, and b43 was never in the game on 6864. `prove` now records each proof in `proofs.tsv` beside the `mod.toml`: the build, the date, every file the install ledger holds for the mod (owner, name, crc32, sha256), and the pass it was seen in (`--evidence DIR`, with its `index.md`'s sha256); `--build`, `--date` and `--pak FILE` record an earlier pass of bytes that are no longer installed. It refuses (exit 3, nothing written) when nothing is installed for the mod or what is installed is not what the ledger put there. `check`, `grade` (the label's `stale(N)` / `unproven`, the release gate), `patchday` (the era a mod is compared from, its `[4]` line, the verdict), `drift` from a mod's folder, `doctor` and `tools/source.py` all ask "proven on N" of the bytes they judge: a recorded proof of N holding every one of them. A build `[proven] builds` lists with no proof for those bytes reads "claimed for other bytes or never recorded" and counts for nothing; the list is kept as written. `release` says whether the pak it wrote is proven (only the same bytes again are). The ledger is one row per file per proof, sorted, and a row stands alone, so two machines' copies merge as a union of lines; a proof that lost a row in a merge no longer adds up to its id and counts for nothing. The three reference skins were migrated from the evidence on disk, not from the old list.
- `install` and `uninstall` refuse under a running game only when it runs from the game folder they were asked to change. A test against a scratch game folder was refused whenever the real game was running; a running game whose executable path can't be read still counts.

- A vanilla log baseline belongs to a build and a scene. `logdiff.py` picked the newest baseline on disk whatever build or hero it was from, so on the day of an update a pass was read against an older build's log without a word, and a second hero against the first one's. It now takes `--build` and `--scene`, falls back only to an older build's baseline for the same scene and says so, and reports a scene with no baseline as not compared (exit 3). `mod_session.py qa --vanilla --restore` saves the baseline; the session index lists each console warning once with its count and whether vanilla prints it too.

- Valve's own heroes lint clean. Packed unchanged and linted deep, 24 of the game's 47 hero models drew the never-allowable M129 and six drew skinning errors. The causes, each fixed: meshes with eight influences store them as eight bytes in a `R16G16B16A16` attribute, or eight 16-bit indices in a `R32G32B32A32_SINT` one (Abrams has 499 bones), and were read as four 16-bit values (M116, M119 on Abrams, Dynamo and four more); the hitbox envelope measured capsules only, where Viscous's head and Dynamo's body are spheres and Haze's torso and Dynamo's pack are boxes; every mesh of a model was measured at once, where a model draws one choice of each body group (Viscous's Goo Ball was judged against the standing hero's hitboxes, and crossed with the standing body in M110); and what Valve's own surface does outside its hitboxes (a gun, Baba's bench, a prop on the ground) was blamed on the mod.
- M129, M130 and M140 count only the overflow Valve's model at the same path does not already have: per hitbox region, our area beyond a line less Valve's there, and a worst point only where it lies further out than Valve's own. Where Valve's own worst point in a region is already past the 10-unit line (Viscous's hands, 21 units from their capsules in the bind pose), the lines are moved out by that stretch, so a surface a hair past Valve's is not "a bit much". The message names Valve's share. An allowance's measure (M140) is that excess.
- M108 leaves alone two of Valve's own pieces sharing a plane where Valve's model has them sharing one (20 of Valve's heroes). M122 judges how far a lower LOD is cut down against how far Valve cuts its own (1.5x Valve's share of LOD0's vertices), where it used a fixed 45% that some of Valve's own models miss.
- M062 compares hitboxes that share a name as a set: Haze, Kelvin, Seven, Baba, the Nurse and the Unicorn each carry two of one name, and Valve's own file read as "changed" against itself. M122 no longer quotes a ratio against a LOD at which Valve's model draws nothing.
- Lint M145 `inside-out-shell`: a closed single-sided piece whose signed volume is negative (the sign is exact), and whose mean thickness (twice the volume over the area) is over a millimetre, so every face points inward; the game culls it from outside. Winding and normals agree with each other there, so M103 and M104 could not see it.
- Lint M146 `lod-inversion`, in the light lint: a material with more triangles at a lower LOD than at the one before (over 1% and 32 triangles, unless Valve's does the same), or a lower LOD reaching more than 0.5 units outside LOD0's bounding box beyond Valve's own reach (0.12 units at most across Valve's heroes).
- Lint M147 `texture-mip-starved`: a new texture whose mip chain stops before the size the game draws it at. From the texture's size and mip count and the UV density on the mesh: over 2 texels of its smallest mip per screen pixel at 8 m.
- M141 also reports a cloth group with no damper at all (vertex attraction 0, what a goal-0 joint compiles to): its swing shrinks by `sqrt(1 - V) = 1` a step, so it never settles, however slowly it sways. A sway under 1 Hz was never reported before.
