# Deadlock and Source 2: what Magician relies on

Facts about the game, its compiler and the tools around it that Magician's code and docs depend on, with the scars that taught them. Everything here was checked on build 6861 or 6864 unless it says otherwise, read from Valve's files, from the compiler's output, or seen in game. **UNVERIFIED** marks a claim nobody has seen in the running game; a fact that comes from community guides and has not been checked here says so.

Facts about Magician itself (its files, commands and gotchas in its own code) live in [../TDD.md](../TDD.md) and [../../CONTRIBUTING.md](../../CONTRIBUTING.md). What the game does under the in-game harness, in detail, is in [../../ingame/README.md](../../ingame/README.md), and what it does under the film kit's free camera in [../../cinema/README.md](../../cinema/README.md). This page is about the platform underneath.

## How the game loads a mod

| Area | Fact |
|---|---|
| Install | The game is `.../steamapps/common/Deadlock/game`; its build number is `ClientVersion` in `citadel/steam.inf`. Assets are in `citadel/pak01_dir.vpk` (with `pak01_NNN.vpk` chunks) and `core/pak01_dir.vpk`. The retail executables are `deadlock.exe` and `vconsole2.exe`; there is no `resourcecompiler.exe`. |
| Mount | Stock search paths are `Game_LowViolence citadel_lv`, `Game citadel`, `Game core`. A mod is mounted by adding `Game citadel/addons` above `Game citadel` in `citadel/gameinfo.gi`. Every Steam update or "verify files" resets that file, and the mods silently vanish while their paks stay in `addons/`. Deadlock Mod Manager mounts `citadel/addons/<profile>` instead. |
| Load order | Addon paks are `pak01_dir.vpk` to `pak99_dir.vpk`, and **the lowest number wins** a path both ship. A search-path folder holds at most 99; Deadlock Mod Manager encodes the same rule and spreads further paks over `addons` to `addons10`. |
| Compiled files | Compiled resources end in `_c`: `.vmdl_c`, `.vmat_c`, `.vtex_c`, `.vpcf_c`, `.vsndevts_c`, `.vsnd_c`. |
| Heroes | A hero's model path is `m_strModelName` in `scripts/heroes.vdata`. Internal names differ from display names: Vindicta is `heroes_staging/hornet_v3/hornet`, Grey Talon `heroes_staging/archer`, Abrams `heroes_wip/abrams`. Keys can share a model: `hero_skyrunner` (unreleased) uses `lash.vmdl`, Paradox's `chrono.vmdl` serves three keys, about twelve test keys use `gen_man`. Four unreleased heroes (Boho, Druid, Fortuna, Graf) name models the build does not ship. |
| Rig | Each hero ships `<name>.vmdl_c` and `<name>.vnmskel_c` (the AnimGraph2 skeleton); graphs live in `animgraphs/animgraph2/hero/` and compile under a `+`-joined name, `hero.vnmgraph+lash.vnmgraph_c`. A replacement must keep bone names, hierarchy and attachments. New animation states are not possible; replacing existing clips is. Patches have moved attachments and changed rigs before (Deadlock Mod Manager shipped repairs after one), so every build is a possible rig break: that is what `drift` and the rig sidecar watch. |
| Model document | A `.vmdl_c` holds far more than meshes. Lash's has 19 hitbox capsules, 49 attachments, 388 anim events, 15 cloth chains and a softbody, 3 LOD groups, and its reference list names the hero's ability particles (`lash_flog_cast_hand_left.vpcf`) and anim-sound tags. A model built from scratch silently drops all of that (lint M061), so a mesh swap goes inside Valve's model document. |
| Particles and sound | Ability particles are `particles/abilities/<hero>/*.vpcf_c`; sound events `soundevents/hero/<hero>.vsndevts_c`; voice lines `sounds/vo/<hero>/`. Sound-event files name their `.vsnd` files as strings in their data, not in the reference list. Source 2 Viewer decompiles both to KV3 text that recompiles to the same thing, so effects and sound events can be authored as text and diffed. Community guides set a sound's loop and compression in an `encoding.txt` beside the wav; that has not been checked here. An event's `base` names one event or a list (`[{ event_name = ... }]`) from `soundevents/base/` and `soundevents/hero/_shared`, and the stack sets the perspective and falloff. Valve renames bases between builds without changing what is heard: on 6868 `Base.Ability.Cast` is `Base.Ability` plus `volume_enemy_targeting_boost_disable_update = 1` only, and `Hero.Default.Melee.Swing` is `Base.Movement.Melee` at `volume -2`, `volume_offset_opponent -3` (its `.Charged` at -3.5 and -8 for opponents), with the swing files in the default, so a hero's `*.Melee.Swing.Charged` names no file of its own. |
| Conflicts | Two mods that touch one shared material or particle collide even when they look unrelated; Deadlock Mod Manager rates a `vmdl_c` collision critical. |

## The hero page

The hero page is Esc, SWAP HERO: the roster. Hovering a card loads that hero's `m_strUIPortraitMap`, a small map VPK at `maps/ui/hero_prefabs/<hero>.vpk`, into `CitadelHeroSpotlight`; the mouse turns `[PR#]root`, the camera's parent. Measured on build 6864, in game unless it says otherwise:

- **Replacing it.** An addon copy at `citadel/addons/maps/ui/hero_prefabs/<hero>.vpk` replaces Valve's and is read on the next hover, also when it is reinstalled while the game runs. The file of the map on screen stays open, so an uninstall of it is refused (`os error 32`) until another hero is hovered. This is why `magician scene` exists.
- **The hero is the panel's own.** The hero drawn there is posed by the AnimGraph `hero_ui`, not by the map's prop: the map's `hero_root` is a `prop_dynamic` with `use_animgraph false` and `kRenderNone`, so its legacy sequence (Lash `hero_pose`, Sinclair `ui_hero_select`) is applied but never drawn. The panel's hero stands where `hero_root` stands (moved to z -4000 it vanished from the page). `hero_ui` has the states Hero_Select, Hero_Info, Hero_Main_Menu, Hero_Matchmaking, Hero_Reveal and Hero_Shop; Lash plays `ui_pose` (`ui_hero_reveal` for the reveal, `ui_shop_idle` in the shop), Sinclair `ag2/ui_pose` for all but the shop, where he plays the in-match `weapon_stand_idle`. Select, Main_Menu, Matchmaking and Reveal play once and hold the last frame; Info and Shop loop. The model streams in about 0.3 s after the hover, so a short piece loses its first beat unless it holds still that long.
- **What renders there.** `info_particle_system` renders (Valve's paths, or a `.vpcf_c` inside the scene VPK at the mod's own path), and so do extra `prop_dynamic`s and a `.vmdl_c` shipped inside the scene VPK. An extra prop needs `rendermode kRenderNormal`: a copy of `hero_root` inherits `kRenderNone` and stays invisible. A non-looping legacy sequence on such a prop plays once at every load and holds its last frame. Valve's own hero-page props (46 of them) mostly hold 1 to 11 frames; the one-shots run up to Dynamo's 300 frames and hold at the end; only Kelvin, Forge, Archer and Deadpack loop (4 to 31 frames).
- **No entity I/O.** The map is client-only: `logic_auto` and `logic_timer` are refused (`Encountered unrecognized client entity in portrait map`), so there are no timers, relays or camera switches. Lights are dynamic `light_barn`s (`directlight "2"`).
- **Cameras.** A `point_camera` on `hero_root` with `parentAttachmentName portrait_camera`, `useLocalOffset true` and origin 0 moves the view onto that attachment. With two `point_camera`s which one draws is not settled: in one test the first in the lump drew, in another a second, unparented camera appended after Valve's parented one drew; parent and order were confounded, one take each. A light parented to an animated prop's attachment swings with it; a camera parented that way is unproven.
- **The silhouette card.** The dark cut-paper silhouette behind the hero is a world mesh of the map, `worldnodes/n0_lr0_c0_s_cb_nomerge<N>_hero_picker_shadow.vmdl_c`: a flat card in world space under an identity node transform, with `materials/ui/hero_picker_shadow.vmat` (pbr, unlit, translucent, a grunge translucency mask `materials/ui/shadow_grunge_trans` scrolled at 4x, and `F_JITTER_VERTICES` at 2 units for the paper wobble). A model compiled at that path and shipped in the scene VPK replaces it. ModelDoc imports an OBJ Y-up: OBJ (a, b, c) compiles to Source (c, a, b).
- Team-reveal maps are gone (the folder is empty).

## The match HUD

What the in-match HUD draws of a hero, read from build 6868's layout and styles (decompiled from `panorama/`) and checked against 1080p captures. `harness/hud_topbar.py` and `harness/hud_native_scale.py` draw a mod's art exactly so.

- **The top-bar portrait is the hero card.** Each top-bar slot holds a `CitadelHeroBadge` of class `TopBar` (`citadel_hud_top_bar_player.xml`), and the badge draws `m_strIconHeroCard` (its `Gloat` and `Critical` forms in their moments), not `m_strTopBarVertical`; no layout on 6868 was found that draws the vertical in a match. The bottom-left health panel (`hud_health.xml`) has no portrait.
- **Its size.** `CitadelHeroBadge` is 88 x 120 px; `.HeroImageContainer` is 80 % of that width; `#HeroImage` has `scaling="contain"`. So the 280 x 380 card is drawn 70 x 95 px at 1080p (a capture measured the dome of one card 64 px wide in it), and Panorama scales by screen height: 94 x 128 at 1440p. Valve's cards are BGRA8888 with 9 Box mips, so the bar samples a mip near that size.
- **Its frame.** `#HeroImage` takes `opacity-mask: hero_badges/hero_image_mask_psd.vtex` (square shoulders above, a half circle below), over `.HeroImageBackground`, a disc of the team colour: `team1Color` #D4860B, `team2Color` #4D75C3 (`citadel_base_styles.css`), #B02727 when the player's health is low and #90FFE3 on a kill streak (`hero_badge.css`). A card is judged at that size, on those colours, beside Valve's: a bust that leaves the face a third of the card's width reads in the bar as a pale shape with a small dark spot.
- **The local player's slot** shows a lit panel of the team colour behind the portrait instead of the disc, and the soul bar lies over the portrait's left edge (seen in captures; not drawn by `hud_topbar.py`).

The ability bar, as it looks on screen (build 6871, 1920 x 1080 captures of four heroes, HUD on, read by Lamplighter's screen reader; the styles are `hud_ability_icon_active.css`):

- **Ready.** Each signature ability is an off-white disc, about 68 px across at 1080p, with the ability's glyph (`m_strAbilityImage`, a white-on-alpha `.psd` texture) drawn dark on it (`wash-color: offBlack`). The glyph square is about 51 px. The four discs sit on a shallow arc, about 89 px apart: the outer two about 13 px lower than the inner two, centres near x = 826, 915, 1004, 1093 at 1080p. The player's key for each sits in a small badge under its disc. Panorama scales the bar with screen height.
- **Cooling down.** The disc turns dark and see-through (the scene shows through it). The part of the cooldown already elapsed is a lighter wedge growing clockwise from 12 o'clock (the mask is mirrored, `scaleX(-1)`). The seconds left are in white digits in the middle.
- **Not ready.** While another ability is being cast or channelled, the other discs go dark with no wedge and no digits (`ability_not_ready`).
- **Active.** A toggled or channelled ability's disc turns lavender for as long as it lasts, for example Seven's Storm Cloud.
- **A cast.** The whole bar dims for about a quarter of a second as an ability goes off. The caster's own cooldown shows on the next frame or two, 40 to 105 ms after the key press.

## Formats

| Area | Fact |
|---|---|
| Resource blocks | Big hero models have 100 or more blocks (an MVTX, MIDX and MDAT set per mesh). Bound the block table by file size, never by a constant. A scan of 15,971 hero files parses with no failure. |
| KV3 | Data blocks (`DATA`, `CTRL`, `PHYS`, `ASEQ`, `AGRP`, `MDAT`) are binary KV3 v4 or v5, LZ4 (method 1) or uncompressed; some model `ANIM` blocks and map entity lumps use zstd. Magician decodes all 18,187 of the game's particles. |
| KV3 writing | A block with blobs (every entity's empty `m_keyValuesData` is one) keeps them in blocks: the count and bytes in the header, a u32 size per blob after the type bytes, `0xFFEEDD00`, the blob data, and a second `0xFFEEDD00`. Without the second marker Source 2 Viewer stops at the end of the stream; with blobs inline it indexes out of range. Magician's own decoder accepts every layout, so reading back its own write proves nothing; written this way, Valve's UI-scene entity lump reads in Source 2 Viewer 21.1 line for line as the original (919 lines, 16 blobs). |
| Meshes | Build 6864 encodes model buffers with meshoptimizer codec version 1 (vertex `0xA1`, index `0xE1`), which older decoders refuse. Index buffers hold absolute vertex ids; `m_nAppliedIndexOffset` is a draw's lowest index and `m_nVertexCount` its highest plus one, metadata and not offsets to add. Blend indices count in the MDAT's own skeleton, matched to the model's by bone name. The weight semantic is `BLENDWEIGHT` or `blendweights` depending on the buffer. Vertex-colour streams are zstd (`m_bCompressedZSTD`). Hero models are hundreds of shells (Valve's Lash welds into 204), and the largest is often a garment, not the body. |
| Bones | Bone count is not capped at 256: Lady Geist's model has 622 skinned joints (226 model bones and her proxy cloth's nodes). But Source 2 Viewer's glb export decoded Lash's retargeted clips exactly only while a replacement stayed small (215 bones); at 235, 251 and 269 the same 43 clips differed (left-hand fingers, the head up to 4.5 degrees, millimetre noise elsewhere). Cause unknown; the in-game effect is UNVERIFIED. |
| Textures | `VTexFormat` on 6864: 1 DXT1, 2 DXT5, 4 RGBA8888, 19 BC6H, 20 BC7, 21 ATI2N, 27 ATI1N, 28 BGRA8888. Hero colour maps are BC7 stored uncompressed, smallest mip first (mip 0 is the file's tail). A colour texture also carries what the compiler packs into its alpha, `TextureTranslucency` (coverage) or `TextureMetalness` (a translucent material writes its metalness to a texture of its own, Materials below), and since BC7 codes colour and alpha together, a colour edit can move the packed alpha (up to 10 levels at metal edges, measured). Panorama's image-list route stores small images, such as the HUD's vertical portrait, as YCoCg DXT5 (Y in alpha, Co and Cg in red and green, a scale in blue; the edit info, `RED2`, says `Texture Compiler Version Image YCoCg Conversion`); read as plain DXT5 they look transparent and wrong. |
| Voice loudness | Voice files (`sounds/vo/`) are mono MP3 inside the `.vsnd_c`; its CTRL block carries the compiler's envelope analysis (`m_pEnvelopeAnalyzer`, the curve M063 and M064 compare peaks on). Perceived loudness (EBU R128, K-weighted) follows that peak only loosely on Valve's own voices: over 400 lines two heroes both record (build 6868, a seeded sample of the 2,348 such lines, measured with ffmpeg's `ebur128`), the correlation between the two heroes' envelope-peak difference and their loudness difference is 0.25, and of the 223 pairs whose peaks are within 1.5 dB, 24% differ by more than 1.5 LU in maximum momentary loudness and 5% by more than 3 LU (integrated: 26% and 3%). So a replacement can match Valve's peak and still sound 1.5 to 3 LU louder, as Valve's own heroes do against each other on a quarter of their shared lines: a loudness rule at those limits would fire on Valve's own voices, and none was written. Magician has no MP3 decoder; the envelope peak is what lint judges. |
| Model game data | A compiled model's `m_modelInfo.m_keyValueText` (DATA) is KV3 text, ModelDoc's GameDataList: on 6877 a hero's holds `CitadelUnitStatusSettings_t` (the health bar on `m_strUnitStatusAttachmentName`, usually `healthbar`, offset by `m_vUnitStatusOffset`), `TaggedSoundSettings_t` (the `scripts/tagged_sounds/<hero>_anim_sounds.vdata` that maps an animation's tags to footstep, landing, mantle and melee-swing events; `heroes.vdata` names no tagged sounds, so the model is the only source), `CitadelCameraSettings_t` (the third-person camera's offsets; `heroes.vdata` has none), `AttachmentCameraData` (the camera-pose attachments and their fields of view, 1 to 12 a model), `CCitadelHeroModelGameData_t` and others. `heroes.vdata` sets its own `m_flCollisionRadius` and `m_flStepHeight` (28 and 24 on 6877, where Haze's model says 20 and 32), so the model's may not be what the hero collides with (UNVERIFIED), and M062 does not judge them. The animation references are DATA's `m_vecNmSkeletonRefs` and `m_animGraph2Refs` (an identifier, `""` for the match and `ui` for the hero page, matched without case: Ivy's Valve model writes `UI`). Older builds' unit status had no attachment name and a fixed offset (`[0, 0, 95]`). M062 reads all of this (`lint::gamedata`). |
| Panorama layouts | A compiled layout's tree is a `LaCo` block (`m_AST`: PANEL nodes, an `id` as a PANEL_ATTRIBUTE); its DATA block is a few bytes. The client library holds as plain NUL-terminated strings the ids its code looks up (`GameTime`, `UnitHealthbar`), the camera pivots it reads (`standing_pivot`, `crouching_pivot`) and the particles it plays by name; `panorama.dll` holds `Unable to find child '%s' in panel '%s'`. |
| Particles nothing names | Of the 18,043 particles on 6877, 3,758 are named by nothing: no compiled file references them (models 185 references, clips 331, particles 13,612), no vdata (8,289 string references), layout (21) or map entity lump (654) names them, and the client code does not. Many look like effects of older versions of abilities. `magician index` writes them to `particles_unreached.tsv` (M084). |
| Power of two | Of 12,598 game textures outside `panorama/`, 143 are not power-of-two: 108 compiler morph atlases (`*_vmorf`), 24 voting cards, 5 minimap, 2 UI and 4 particle sheets, none under `models/`. Inside `panorama/`, 1,556 of 2,142 are not. |
| Valve's loose ends | The shipped game has references that resolve to nothing: `soundevents_manifest_devonly`, an unused Lady Geist test book (`panorama/layout/books/book_test`), three Haze and Viscous particle refs, and on 6864 six more in `inferno_v4` materials that name `heroes_wip/infernus` textures the build doesn't ship. Lash's response rule `Lash_Use_Ground_Pound` (`scripts/talker/response_rules_lash.vrr_c`) names `lash_use_power1_02_02_ability_3d`, an event no sound-event file defines, so about one Ground Strike in eleven logs `Attempting to play invalid sound event` and then `Unable to determine duration for response for rule 'Lash_Use_Ground_Pound'`. That is vanilla; don't "fix" it in a mod. Lint blames a mod only for references it introduced. |

## The compiler (CSDK 13)

Valve's `resourcecompiler.exe` comes with the community CSDK, not with the retail game; CSDK 13 is built on the Dota 2 Workshop Tools. The setup, from the community's guide: unpack it outside the game folder and outside OneDrive, rename `readonly_tools_asset_info.binOFF` to `.bin`, keep addon names lowercase without spaces, and have Steam running. Sources live in `<csdk>/content/citadel_addons/<addon>/`, outputs land in `<csdk>/game/citadel_addons/<addon>/`. The command is `resourcecompiler.exe -i <absolute path> -game <gameinfo.gi> [-r] [-f] [-v] [-nop4]`; each output is the source's extension with `_c`.

On Linux it runs under Wine (9.0, Ubuntu 24.04's, 64-bit only, no Steam running), with every path given as Wine names it (`Z:\...`): a full compile of a hero skin's addon (models, materials, textures, particles, sounds, Panorama) needs no GPU and gives the same bytes as on Windows, file for file, except a model's distance-field block (`DSTF`), which the compiler does not repeat from one run to the next (two compiles under Wine differ there as much as Wine and Windows do). A Wine prefix is made on first use, in a folder that must already exist.

| Issue | What happens | How Magician handles it |
|---|---|---|
| Byte-order mark | A UTF-8 BOM at the start of a vtex, vmat, vpcf, vsndevts, vmdl, vdata, vcss, svg, kv3 or dmx source makes it fail (`Expecting a .vtex file`). Windows PowerShell 5.1's `Set-Content -Encoding utf8` writes one. | `build` refuses such a source by name and never rewrites it. Write with `[IO.File]::WriteAllText` or PowerShell 7's `-Encoding utf8NoBOM`. |
| Hang | It can print `OK: N compiled, 0 failed` and then hang on exit (`Timed out waiting for thread to exit? hung?`). | `build` ends it 20 s after the summary. |
| Whole-addon input | Fed `-i <addon>/* -r` it tries every png, dmx, fbx and `.gitignore` (`Failed to find compiler`). | `build` compiles real sources only. |
| Stale outputs | Outputs whose source was deleted stay in the game-side folder forever, and a live file that still names one pulls it into the pak. | `build` packs only outputs that map to a live source and fails on a live-to-stale reference; lint M032 catches it in a shipped pak. |
| Default textures | It writes its own copies of the engine's default textures (`materials/default/default_*_tga_*.vtex_c`, 2,232 bytes against Valve's 2,184) into every addon that compiles a material. Shipped, they replace the global fallbacks. The copies in three published mods (6868) decode, every mip, to the same pixels as Valve's file at the same path, or sit at a path Valve does not ship (`default_mask_png_*`, from PNG sources), which only the mod's own materials read: neither changes what the game draws. | `build` leaves them out; lint M071, an error only when the pixels differ from Valve's. |
| Content tree | `-i` refuses a file outside the CSDK content tree (`Unable to determine mod from file`). An addon junctioned into `content/citadel_addons/` compiles through the junction path, not the repository path. | Keep addon sources in a repo and junction them in. |
| Roughness | Roughness textures must be power-of-two (`Cannot filter non-power-of-two texture`, the `HemiOctIsoRoughness` mip filter), or the vmat fails. | Bake at power-of-two sizes. |
| Zero-area triangles | A render mesh loses some zero-area triangles (46 of about 16k on one body's LOD0, 147 on its LOD1 and 2); Valve's own body keeps all of its 125,573. Nothing visible is lost. | Accept a shortfall up to the mesh's own zero-area count. |
| Model-only bones | Bones a render DMX declares (cloth chain bones) are sorted into the hierarchy, so later Valve bone indices shift, and the cloth FeModel grows (Lash: 75 to 91 nodes for four four-joint chains). Animation binds by name and decodes identically. | Compare models by bone name, never by index. |
| Animation pose | A model bone takes the model-space pose of the animation skeleton's bone of the same name, case aside (Kelvin's and Viscous's models have `pelvis` where their `.vnmskel` has `Pelvis`); a bone the animation skeleton lacks follows its model parent at its bind offset. Valve's own heroes ship models whose hierarchy is not their animation skeleton's (a `weaponHand_L` under `weapon` where the animation holds it under `root_motion`, a hose under `hand_R` where it holds it under `weapon_hand_R`, 6875) and play, and Source 2 Viewer retargets clips the same way. A model's bind is not its animation skeleton's reference pose either (Viscous's fingers sit 11 units from theirs). A reparented bone on a mod has not been watched in game: UNVERIFIED. | `lint::carry`: M062 judges a reparented bone by what the mod hangs on it, against Valve's model's bind, never against the reference pose. |
| Round trip | Recompiling Valve's own decompiled `lash.vmdl` unchanged is not byte-identical to the shipped file (renumbering, re-encoded animation, 1e-6 float noise). Valve's materials (`models/heroes_wip/lash/materials/*.vmat`) are illegal resource names to the CSDK and are only referenced, never loaded. | Prove a mesh swap against that round trip, not the shipped file. |
| Quaternions | Attachment rotations can come out with either sign, `(0,0,1,0)` against Valve's `(-0,-0,-1,-0)`: the same rotation. Cloth compiles to `$`-named nodes in the bone list (`$cloth_m0p12`, `$cc<joint>_0`). | M062 compares rotations sign-free and skips `$` nodes. |
| Tagged-sound clips | Clips with a `CNmClipDocEvent_TaggedSound` event fail under CSDK 13's default `bin/win64` (the Dota tools of Oct 7): `Failed to allocate an instance of class 'CNmClipDocEvent_TaggedSound'`. | `build` picks `bin/win64_nm` for such clips: make it as a copy of `win64` with Deadlock's own (Oct 20) `resourcecompiler.dll` and `animationsystem.dll`. An addon's `.magician-compiler` file or `--bin` names another folder. |
| Distance fields | A model's `DSTF` block (one signed-distance grid per bone, the ambient occlusion it casts) comes only from a `DistanceFieldList` node in the model document, and Source 2 Viewer's vmdl decompile writes none, so a document patched from a decompile drops Valve's fields with no word from the compiler (Valve's Lash: 25 fields). The node allocates only when the compiling gameinfo's ModelDoc features include `distancefield`; retail Deadlock's has it, the CSDK's `game/citadel/gameinfo.gi` does not (`Failed to allocate an instance of class 'DistanceFieldList'`). Each `DistanceField` (keys `resolution`, `surface_bias`, `distance_offset`, `two_sided`, `far_field_only`, `use_for_occlusion`, `use_for_collision`, `parent_bone`, `extra_boundary_voxels`, `filter_bone_influence_threshold`, `filter_bones`, `exclude_materials`, `body_group_name`, `body_group_choice`) needs a `DistanceFieldFromRender` child with `meshes = [ ... ]` (render mesh names; without them it traces nothing and the field is dropped). `resolution` N is cells across the traced geometry's longest extent, and the compiled grid adds one cell each side (a compiled 18 is an authored 16); a triangle is traced when the mean over its corners of its weight on `filter_bones` exceeds the threshold; `parent_bone` compiles to `m_nParentBoneNameHash`, MurmurHash2 of the lower-cased name with seed `0x31415926`. Fitted to Valve's Lash and clone turret (within a cell on 17 of 25 and 17 of 22 fields): threshold 0.5, the bone and its `_TWIST` bones, 48 cells on `spine_0`, 32 on the head, clavicles and scapulae, 8 on the balls of the feet, 16 elsewhere, occlusion on, collision off, one-sided. **UNVERIFIED** what restoring them changes on screen: in one in-game test `r_distancefield_enable 0` changed nothing visible. Two compiles of one document do not give the same `DSTF` bytes. | `build` and `release` compile a document with a `DistanceFieldList` against `<csdk>/game/citadel_dstf` (the CSDK's gameinfo plus that one feature), and say before the build when a document replaces a Valve model with fields and asks for none; M142 says it after. Writing the node is the mod's: which pieces should cast occlusion is a choice. |
| Panorama images | Images compiled through a `panorama_image_list` vdata (the CSDK's `hero_image_template` route) come out with one mip, BGRA8888, and the 120x200 vertical as DXT5; Valve's hero cards (280x380) carry nine Box mips and its vertical is BGRA8888 with one. Ours alias when drawn small. No option in a per-image `.txt` brings the mips back (`nomip`, `nolod`, `maxres`, `mip_filter_strength`, `output_format` and `forcebc3` change nothing; `nocompress 1` gives RGBA8888, not BGRA8888). | Compile those through a per-image `<image>_psd.vtex` (it compiles to the same `_psd.vtex_c` path): `m_inputTextureArray` on the PSD, a `DilateColorInTransparentPixels` input processor, `m_outputFormat` `BGRA8888`, `m_mipAlgorithm` `Box` for cards and `None` for the vertical, `m_bNoLod 1`. Generate it, compile, delete it: with the image list also present, a whole-addon build races two sources for one output. The one-mip icons can stay on the image list. |

### Which CSDK it is

`magician csdk` reads these from the kit's own files; `doctor` and `build` say the version and the gaps that matter.

- **Telling 12 from 13.** CSDK 13's `read_me.txt` says "Community SDK Version 13", and its binaries are `game/bin/win64` and `game/bin_server/win64`. CSDK 12, from the community's pages (deadlockmodding.pages.dev, CSDK 12; not seen here), ships four sets, `bin`, `bin_tools`, `bin_server` and `bin_cs2`, chosen in its launcher: `bin_tools` previews projected particles and crashes compiling AnimGraph1, `bin_cs2` is only for the GUI map compiler's lit maps. The gameinfo's `UserSettingsFileEx` reads `csdk14_` in CSDK 13: it is not a version.
- **Whose tools.** CSDK 13's `bin/win64/resourcecompiler.dll` is dated 2026-10-07 (Dota 2's Workshop Tools of that day); Deadlock's own of 2026-10-20 sits beside it as `-resourcecompiler.dll` and is the one `bin/win64_nm` uses.
- **Its own game files.** The kit compiles against its own copy of Deadlock's files, not the installed game: CSDK 13's `game/citadel/steam.inf` says `ClientVersion=6836` (Oct 31) while the installed game is 6875. Shaders, engine defaults and the gameinfo come from that copy.
- **Gameinfo.** CSDK 13's ModelDoc features are `modelconfig;wireframe_backfaces;animgraph;animgraph_compatibility_force;editorconfig;gamepreview`; retail 6875's are `modelconfig;gamepreview;wireframe_backfaces;distancefield`. Both say `tonemapping 0` at the top and `Tonemapping 0` under SceneSystem, and both list `directional_irradiance_sh2_lum` among the lightmap channels, so the dark Hammer bakes the kit's readme reports (SH2_lum missing, Oct 20) are in the light baker, not the gameinfo. Not reproduced here.
- **Packing in the kits.** CSDK 12's documented route is the asset browser's CS2 Workshop Manager (a VPK of the addon's game folder, 2 GB at most; a "multichunk" manager splits bigger ones), and both kits' launchers have "Create VPK" on an addon's menu (deadlockmodding.pages.dev, Packing an Addon, CSDK 12 and 13). CSDK 13's `csdkcfg.exe` is a Rust program with a VPK writer of its own (its error strings name chunk files). Measured on Maid Lash's addon (2026-11-27): Create VPK packs the whole of `game/citadel_addons/<addon>/` into one v2 VPK named after the addon (not `pakNN_dir.vpk`), with the 48-byte MD5 section, which Source 2 Viewer's `--vpk_verify` accepts; two runs gave the same bytes. It held 565 files against `magician build`'s 551 from the same folder, every shared file byte-identical: the 14 more were the compiler's 9 copies of engine-default textures (M071) and 5 stale outputs whose sources were gone, one of them a probe. A file at the folder's root is written under an empty directory name, where the format expects a space, so the tree ends early and the pak reads as empty: Source 2 Viewer listed no file in it. Magician's builds used to leave `magician_build.stamp` and `magician_build.log` there; they now live in `game/.magician-build/<addon>/`.
- **Magician's pak against it.** `pack`, `build` and `release` write one v2 VPK, entries sorted, every file inline, no MD5 section (Source 2 Viewer's `--vpk_verify` says "no checksum section"; the game loads it), the same bytes for the same files, and only outputs that map to a live source. Over 2 GiB it refuses rather than split.

### Skinning streams, hitboxes and body groups

- A mesh with eight influences per vertex does not store them as its attribute formats read. `BLENDINDICES` as `R16G16B16A16_UINT` is eight one-byte bone indices, as `R32G32B32A32_SINT` eight 16-bit ones (models past 255 bones: Abrams has 499); `BLENDWEIGHT` as `R16G16B16A16_UNORM` is eight one-byte weights. `R8G8B8A8_UINT`, `R16G16B16A16_SINT` and `R16G16_SINT` are four, four and two indices; `R8G8B8A8_UNORM` and `R16G16_UNORM` four and two weights. Checked against Source 2 Viewer's reader and on every hero of 6865 (weights sum to 1 on all of them).
- A hitbox (`m_nShapeType`) is a box in its bone's frame between `m_vMinBounds` and `m_vMaxBounds` (0), a sphere at `m_vMinBounds` (1) or a capsule between the two points (2), the last two with `m_flShapeRadius`. Most heroes are capsules only; Viscous's and Haze's heads and Dynamo's body are spheres, Haze's torso and Dynamo's pack boxes.
- A model draws one choice of each body group. `m_meshGroups` names the choices (Viscous: `default_@0_#&body`, the standing hero, and `default_@1_#&inflated`, the Goo Ball), `m_refMeshGroupMasks` gives each mesh the choices that draw it, and `m_nDefaultMeshGroupMask` the choices drawn by default. Meshes of two choices are never on screen together, and another choice has its own hitbox set (`inflated`). Magician measures the default choice against the `default` set; what another choice looks like is not judged.
- Valve's own surface lies outside its hitboxes on about half the heroes of 6865 (guns, Baba's bench, props laid on the ground in the bind pose, bodies the capsules were never fitted to): up to 48 units and half the visible surface. A fair-play measure of overflow is only meaningful against Valve's model at the same path.

### Cloth

What the compiler makes of a ClothChain joint, read back from the compiled FeModel (`magician cloth`, or `Source2Viewer-CLI -b PHYS`), measured on Valve's Lash and on lab compiles:

- `goal_strength` g compiles to `flAnimationForceAttraction` F = g³, exactly (all 32 free nodes of Valve's Lash, authored g 0.15 to 0.375, and every lab node from g 0.05 to 0.6).
- `goal_damping` d compiles to `flAnimationVertexAttraction` V = F + h(g, d), and V is 0 whenever g is 0 (a goal-0 node has no damping at all). h is about 2d / g^1.5 while small and saturates toward 1: on Valve's Lash d 0.0025 gives V − F 0.021 at g 0.375 and 0.054 at g 0.2; in the lab d 0.0005 gives 0.031 at g 0.1 and 0.0019 at g 0.6. The old rule of thumb `1 - (1 - d)^64` is right only near g 0.1, and a mod tuned by it compiled 0.28x to 2.8x the damping it asked for. Read V back instead of trusting a mapping.
- `gravity_z` compiles to `flGravity` = 360 × gravity_z; `stray_radius` to `m_AnimStrayRadii`; `bend_spring 1` to a rod two joints up plus a bend; `antishrink a` to a minimum rod length of a × rest; `suspender` to a stretch-only rod from the root; per-joint `drag` to nothing.
- `extrude_sides 2` turns a joint into two side nodes `$cc<joint>_0/_1` at ±`extrude_radius` along the joint's local Y (twist 0), with cross and diagonal rods, and the bone takes the ribbon's roll. A joint's parent may be any earlier joint, so chain trees compile.
- The FeModel carries each node's rest transform in model space (`m_InitPose`: position, scale, rotation), and a collision shape's spheres are in the frame of its node. Rods are compiled from that pose: on 6865 the rest distance lies inside the rod's interval on 44 of 47 heroes and on all three reference skins, so a rod that disagrees with the rest pose is not something a mod produces.
- Valve's cloth is not tidy, which is why Magician has no absolute rule on it. On 6865: free nodes rest inside a collision shape of their own layer on most heroes (Lash's neckties 3 units into the chest capsule, Werewolf's tail 10); the way out of that shape is further than the rod to a static node allows on 16 heroes; half of all rod and shape pairs could pass the shape between two nodes; goal-0 nodes with no damping exist on seven heroes; and a node's linear settling time runs from 0.2 s to over two minutes (Wraith). A cloth rule has to compare a mod's group with Valve's group at the same place, or stay silent.
- A cloth proxy DMX's per-vertex maps compile the same way: `cloth_goal_strength_v2` to g³, `cloth_goal_damping` by the law above, `cloth_gravity` to `flGravity` as given (units/s²), `cloth_collision_radius` to the node radius, and a `cloth_stray_radius$0` map (Valve's proxies carry none) to `m_AnimStrayRadii`. A proxy with the same geometry binds the render mesh to the same faces.
- Valve's free nodes are not all "g 0.1": Lash's neckties, hair, rope and glove ring are 0.375, his can 0.35, the wieners 0.25, the wraps 0.2, the anchor ring 0.15; Celeste's ponytail and ribbons are 0.1; Sinclair's coat-tail proxy 0.215.
- Shapes (`nCollisionMask`) and nodes (per-node tree masks) carry collision layer bits. That a node and a shape must share a layer to collide is UNVERIFIED in game.
- CSDK 13 leaves the **last joint of an extruded chain unoriented**: it gets no node base (`m_NodeBases`) and no reverse offset (`m_ReverseOffsets`), and its ctrl is listed in `m_FreeNodes` with the side nodes; the joint before it is placed from the tip's side node. So the tip bone keeps its animated pose while the cloth moves, and whatever is skinned to it bends back toward where it was drawn. Lab, 2026-11-25 (Maid Lash's five-joint ribbons): the same whatever is last (drop the fifth joint and the fourth loses its base), with or without a stray radius, with the root rotation-locked or not. An un-extruded last joint (`extrude_sides 0`) compiles as one simulated node with a base built from the previous joint's side nodes, and the previous joint is placed from it. Valve's shipped extruded chains (Astro's and Synth's scarves, Lash's rope) do have their tips oriented, so Valve's compiler differs here.
- No per-node air drag reaches a chain: the joint key `drag` leaves `flPointDamping` at 0 and `mass` only changes `m_NodeInvMasses` (lab, 2026-11-25). On 6868 every Valve hero compiles point damping 0 on every node, `m_flLocalForce` 1 and `m_flLocalRotation` 0, windage 0; ClothParams air drag (velocity and quadratic, whole model) is set on three: Kelvin 0.07, Calico 0.01, Sinclair's illusion (`wraith_magician`) 0.05. Valve's long loose pieces get their look from goals and damping instead: Astro's scarf (five extruded joints) goal 0.5 mean, vertex attraction 0.16, gravity 540, radius 1; the Nurse's ribbons goal 0.41, vertex attraction 0.16 to 0.25, radius 3 to 4; Chessmaster's scarf and coat tail goal 0.62 to 0.64; Synth's scarves 0.2 with radius 2.5.
- `m_flLocalForce` 1 does not keep the hero's airborne motion out of a chain: a ClothChain node feels his fall (sv_gravity 800 units/s², faster in dives) and his pulls. Seen in game on Maid Lash's ribbons (6868): compiled with gravity 356 and near-zero goals they stood straight up in every jump and fall; at 4275 they hung through the body. In Lash's Grapple dive and Ground Strike plunge the net force on a chain points up even at 1.5 times his fall.
- A chain tuned on its clips alone can look dead in game: on 6868 Lööps Viscous's first settings had ears on a 0.6 leash and dome rings on a 0.7 leash, and the hero's accelerations (his fall at 800 units/s², a sprint start of about 1800) pressed them to the leash through every move, so they moved and stopped dead (settling in 0.1 to 0.2 s in the solver model). `magician cloth` prints, per chain, the steady offset under the fall against the leash: the dome rings sat at 10 times theirs.
- A stray radius (`m_AnimStrayRadii`) at or above twice a node's arc length from its last static node never engages: the rods keep the node and its goal each within one arc of that node.

## Sound stacks and music

A sound event is only as clever as its type, and a type is a stack of operators (`soundstacks/*.vsndstck`, listed in
`soundstacks/soundstacks_manifest.vrman`; core types in core's `soundstacks/soundstacks_manifest_core.vrman`).
Measured on build 6868 with a probe pak on a stock hero, `snd_showstart 1`, and a loopback recording of the speakers
(tones on their own frequencies, read back by frequency):

| Area | Fact |
|---|---|
| A mod's own stack types | An addon copy of a stack file the manifest already lists, with new stacks appended after Valve's, loads in retail and events of the new types play. `soundstack_citadel_seasonal_fireworks.vsndstck` is the last file in the manifest's last group, so a stack there can import every citadel type; Valve's own stack in it recompiles to the same text. To compile, the addon's content folder needs the decompiled manifest and every stack source (citadel's and core's `soundstacks_core`, `_core_setters`, `_src1`, `_soundscapes_core`, `soundstacks_manifest_core.vrman`): without them resourcecompiler fails with `Missing operator stack manifest soundstacks/soundstacks_manifest.vrman` and crashes. | Wrapping a hero's event | Retyping a hero event to a stack that imports Valve's type whole (`sos_import_stack` of `citadel_perspective_default`, `auto_connect_public_fields`), with its base given as `base = [{ event_name = "<Valve's base>" field_name = "citadel_perspective_default" }]` and every other field unchanged, plays the same file at the same level: in a loopback recording the wrapped reload-start file came back at -42.8 dB against its source, the unwrapped reload mid and end at -42.6 to -43.0. Lint M063 reads such a base as empty. |
| Child events | `soundevent_start` with `input_start` held at 1 starts its event once; the child outlives a parent whose file ends (an 8 s child of a 1.7 s cast played to its end). With `input_start` = `soundevent_get_info`'s `output_unstopped` the child stops when the parent is stopped (a loop that ends when an ability is cast). |
| Beat queue | `citadel_music` (`track_queue`): an event queued on its own track with `sync_track_name` set to a playing music track starts on that track's next beat (`sync_bpm`), about 6 ms after it (two starts queued at one moment began 1.7 ms apart). Queuing the playing event again on its own track restarts it from its `startpoint` on the next beat: the bar position resets and the beat steps by 6 to 37 ms each time, `block_equal_priority "true"` notwithstanding. A `citadel_music` event plays its file once and stops (it does not repeat at `endpoint`); a file compiled with a sampler loop (`smpl` chunk: `LoopStart`/`LoopEnd`) loops sample-exactly in an 8-track 2D voice (116 s of a 4-bar click loop: beat jitter 0.09 ms rms, drift 0.1 ms a minute). MP3-compressed loops keep their length and seam (decoded sample count equals the source's, the seam matches the source within the codec's noise). |
| Opvars | `opvar_set_float` on a stack, operator and field a mod names (none of them Valve's) is read by `opvar_get_float` in another event's stack: a layer of a running music voice came in on a cast and went out after its hold. The names may be `@public.<field>` references. `core_setter_stack_opvar` (core) works from a hero event. Valve publishes `citadel_global_opvars` (`citadel_game_time`), `citadel_relevance_opvars` (`player_health_fraction`, ...) and `citadel_dialog_opvars` (`dealt_recent_damage`, `received_recent_damage`, `is_enemy_in_proximity`, which is hidden information) to any stack that reads them. |
| The music slider and layer | A 2D event with `event_use_music_convar true`, `event_voice_layer "ui"` and `mixer_mixgroup "Music"` follows `snd_musicvolume`: at 0 a hero's music children were silent while the hero's own cast and reload files still played. |
| Layered hideout music elsewhere | A hero event of type `citadel_music_hideout` starts its voice outside the hideout (logged) but is silent: its layers' levels come from hideout-only opvars (the play button's distance, menu pages). |
| One instance of an event | Neither the event fields `limiter_on 1`, `limiter_max 1`, `limiter_stop_oldest false` nor `block_is_untimed true` (`block_match_entity false`) let the first instance of a 2D music event live and refuse the next: with either, no instance started at all. A stack's own join of Valve's per-event-name limiter group (`soundevent_group_join` on `limiter_global_event_distance`, `input_limit_max_events` 1, an increasing birth number as `input_match_float`) did not stop a newcomer either. What works is a heartbeat: the running event writes its own `soundevent_get_info` `output_elapsed_time` to an opvar every frame, and whatever would start another samples that opvar at its birth and 0.12 s later and starts one only if it stood still. |
| Clocks a stack can read | No game clock reaches a stack on 6868: a singleton keyed on `citadel_global_opvars` `citadel_game_time` never blocked (the value did not advance as a clock in a hero event's stack), `soundevent_get_info` `output_host_elapsed_time` is per event, and `sys_get_time` (in core's legacy stack file, commented out) does not exist in the KV3 operator set. Music cannot be anchored to the game clock, so a material animated on `time` can share a tempo with a music event but not a known phase. |
| Silent starts are refused | A 2D event whose computed level at its first frame is below `block_volume_min` (base_3d) never starts: an 8-track event whose every track began at -inf dB (levels eased up from 0) was refused until the event set `block_volume_min -1` (Valve's music bases do). |
| `sync_bpm 0` | A `citadel_music` (`track_queue`) event with `sync_bpm [0.0]`, with or without `syncpoints`, never starts. A phrase queued against a sync track on which nothing plays starts at once. |
| Queued events and `delay` | An event's `delay` field does nothing once the event is queued (`citadel_music`): a queued phrase given `delay 4` started on the next beat. To start one later, start it from a stack that waits (`soundevent_get_info` elapsed against a delay, `soundevent_control` `input_add_dependent` to keep the waiter alive); it is then queued as usual. A `track_N.track_percent_chance_to_play` (0 to 1 in Valve's events) on a queued 2D event did not stop it playing; a `math_random_float` (execute once) in the waiter is the chance instead. |
| Whose event it is | The perspective a wrapped hero event computes is the listener's: an enemy bot of the same hero, its reload-end file played on our client, did not pass the player gate (`math_perspective_is_player`), so its children did not start. One event seen; a fighting bot was not achieved. |
| The log | `snd_showstart` prints `src 0` for every sound on 6868, so it cannot say whose entity a sound was on; `time` is the sound system's clock. |
| Recording the game's sound | WASAPI loopback of the default output device (shared mode, `AUDCLNT_STREAMFLAGS_LOOPBACK`) hears the game; packets come only while something plays, and the stream's device position can restart mid-take, so place packets by their QPC time, not by device position alone. |

## Source 2 Viewer

Source 2 Viewer (ValveResourceFormat, MIT) is the independent reader every Magician decoder is checked against, and the exporter the Blender QA reads. Pin its version: CLI flags change between releases. 21.1 is the one used here. Its authors ask projects built on it to credit "Powered by Source 2 Viewer", and the MIT notice goes with its binaries if they are ever shipped.

- `Source2Viewer-CLI -i steam:1422450/game/citadel/pak01_dir.vpk -l` lists; `-d -o <dir>` decompiles; `--gltf_export_format glb` exports; `-b PHYS` prints a block; `--vpk_create` packs; `--kv_flatten` gives diffable KV. Exit codes are 0, 1 and 2. `--game steam:...` needs the install's `gameinfo.gi`, which is missing while Steam validates.
- `-d` on a single compiled file also writes the exported PNGs next to the input. Decompiling inside an addon's game folder litters it (lint M011 catches what ships).
- The glb export carries LOD0 only (`--gltf_mesh_list` cannot pick LOD1 or 2; count those from the compiled `MDAT` blocks, `-b MDAT`) and names meshes `<model>.<mesh>`. It loads a model's clips from the input VPK before the game, so a mod's model and its clips packed into one VPK export together. Additive clips export as raw deltas unless `--gltf_compose_additive`.
- Blender truncates ID names to 63 bytes, so long clip paths collide on import and one clip silently stands in for another (Lash's `ability_groundstrike_airdrop` and `_airdrop_loop`). `qa/glb_clips.py` renames them first.
- The Debug GUI has an MCP server (`--mcp`, `tools/s2v_mcp.py`; the GUI is Windows Forms, so it starts on Windows) with a camera, a time step and screenshots, so an asset render is repeatable without the game. While it has had a model open it keeps the game's paks mapped, `citadel/addons` included, and `magician install` then fails with `os error 1224`; a game launched after that runs the old pak. It also locks any VPK it opened a file from, so a pack step onto that VPK fails without a word. Stop the viewer before installing or launching, open files from a scratch copy, and check `magician install --status` shows the crc you meant.
- Its renders are shading evidence, not proof of what the game does.

| Area | Fact |
|---|---|
| Test maps | The Hero Sandbox is `new_player_basics` (`selecthero hero_<name>` inside it, no cheats needed). `map hero_testing` crashes `client.dll` about 25 s after load on 6864, mods or not; so does launching with `-dev` when it loads. The city is `dl_midtown`; `dl_hideout` also loads. `street_test` from older guides is gone. The shipped `cfg/citadel_sandbox_match.cfg` sets `sv_cheats 1`. |
| Commands | Retail has no netcon. Release commands include `map`, `exec`, `citadel_hero_testing_enabled`, `citadel_create_unit`, `spawn_hero_testing_controller`, `citadel_hud_visible`, `host_framerate`, `playdemo`, `demo_gototick`, `demo_pause`; with `sv_cheats 1` also `noclip`, `setpos`, `setang`, `mat_wireframe`, `mat_fullbright`, `r_drawparticles`, `particle_test_create`, `citadel_spawn_all_heroes_in_a_line`, `host_timescale`. `screenshot`, `png_screenshot`, `startmovie`, `reload_model` and `freecamera_*` are development-only and dead in retail: capture through the OS. The flags in the game's command dump (SteamDB's GameTracking, `DumpSource2/convars.txt` and `commands.txt`: `release`, `cheat`, `developmentonly`) don't settle it: `thirdperson` (cheat) and `cam_*` (archive) do nothing. |
| Clean frame | `citadel_hud_visible 0` hides the HUD, crosshair, minimap, kill feed, a demo's playback bar and the GAME IS PAUSED banner, but not your own health bar or any unit's overhead bar. `r_drawpanorama 0` (cheat) also hides your own bar, world labels, damage numbers and the console itself (the harness then drives it blind), but not other units' bars: those are world panels (`panorama/layout/unit_status_overlay_v2`), removed only by an override of `panorama/styles/unit_status_v2.vcss`. `cl_hud_telemetry_*_show 0` takes the corner text off. `exec` finds `cfg/*.cfg` inside an addon VPK. |

Quality settings (`mat_viewportscale`, upscaling, anti-aliasing, depth of field, shadows) are development-only cvars: set them in the video menu (`cfg/video.txt`). |
| Cameras | `citadel_camera_overrides_enabled 1` with `citadel_camera_override_{x,y,z}_offset` (x -400 to 100, y and z -150 to 150) and `_fov` (50 to 150) works, also during demo playback, even paused. `citadel_camera_inspect_mode 1` (cheat) orbits the camera round your hero with the mouse, and injected mouse moves turn it. | Repeatable shots | Record once, then `playdemo`, `demo_gototick` and `demo_pause` to the same tick on every build. Left Shift is the demo spectator's fly-up even with the console open, which is why `console.py` types with Right Shift. |

| Panorama script | Panorama's JavaScript has `$.Schedule`, `$.DispatchEvent`, `$.RegisterKeyBind` and `$.Msg`; `$.AsyncWebRequest` is removed (`AsyncWebRequest has been removed.` in `panorama.dll`), and there is no game API object (no player position). Shipped layouts run console commands through the panel event `CitadelConCommand('<cmd>')`; the film kit's bridge does the same every rendered frame. |
| What the log testifies | On 6868, with `-condebug`: `[ResourceSystem] Failed loading resource "<path>" (ERROR_FILEOPEN: File not found)` for a resource asked for and missing; `Unable to lookup attachment "<name>" on model "<model>"` when an effect asks a model for an attachment it lacks (vanilla prints one for `ability_apply` on model `""`); `[MeshSystem] Model <m>: Attempted to attach attachment <a> to an unknown bone <b>!`; `Camera Pose Node "<node>" has a noticeable height overshoot vs the standing pivot ( <v> ) ... Zeroing.` and `VMDL Camera Pose Success! "<model>"` when a hero model's camera attachments (`near_`, `far_`, `gunaim_`) load (Abrams prints nine overshoots in vanilla). | Command pipes | `engine2.dll` has console command pipes (`-concommandpipe`, which requires `-insecure`, so VAC off) and VConsole2 (`vconcomm.dll`, no listener without a flag). Both need launch flags nobody passes to the shared game, so neither has been tried. |

## Hazards outside Magician's own code

| Area | Issue | What to do |
|---|---|---|
| Steam | Updates stage on the library named by `StagingFolder` in `appmanifest_1422450.acf`; a full system drive fails them ("not enough disk space"). A repair can be started headless with `steam.exe -silent steam://validate/1422450`; it is done when `StateFlags` in that manifest is 4. | Point staging at the library's own drive. |
| Mod managers | Deadlock Mod Manager 2.3.0 renumbers every `pakNN_dir.vpk` in `addons`, including files it didn't install, and rewrites `gameinfo.gi` in its own layout. Magician's ledger then names files that are gone. | Magician follows each ledger row's crc to the pak that now holds those bytes (`install --status` shows the move, `patchday` checks it under its new name, the next install or uninstall writes it down). An update of a renamed pak is refused with the `--as` that replaces it in place. |
| Two installers at once | Two installs or uninstalls at once each rewrote the ledger from what they read, and one row was lost. | Magician holds `.magician-installed.lock` in `addons` for each read, change and rewrite of the ledger; another installer that edits the folder at the same time is outside it, so don't run one beside Magician. |
| Stuck keys | A scenario that dies between `@down ctrl` and `@up ctrl` leaves Ctrl held for the whole desktop: every typed command becomes a chord (nothing reaches the console, though F7 still toggles it), Enter opens party chat and Esc becomes Ctrl+Esc, the Start menu, which takes the foreground. A `.console-blind` file left by a closed game sends the next one blind from the wrong state. | `console.py` releases held keys however a run ends, clears stuck modifiers first, and trusts the blind-state file only if it is newer than the running game. |
| Disk | On a spinning disk, reading VPK entries in directory order instead of (archive, offset) order makes a scan about 18 times slower. | Magician's whole-game scans sort their reads by archive and offset. |
| Mod policy | Valve has made no statement about mods. By community consensus, cosmetic client-side VPKs carry no known bans, while visibility advantages and memory reading do. | Stay cosmetic: that is what fair play lints for. Nothing here makes a mod ban-safe. |
