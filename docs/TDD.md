# Magician: technical design

How Magician is built and why. What it is for is in [PDD.md](PDD.md); facts about the engine itself (formats, compiler behaviour, what the game does at runtime) live in [reference/engine.md](reference/engine.md), one fact in one place.

## The model: mods are programs, builds are targets

| Compiler idea | In Magician |
|---|---|
| Target | A game build, identified by `ClientVersion` in `game/citadel/steam.inf` |
| Target description | The build's **baseline** (`baseline.tsv`: every path, CRC and size in `citadel` and `core` `pak01_dir.vpk`) and two sidecars: the **rig** (`rig.tsv`: every skeleton's bone list and every anim graph's control parameters) and the **engine** (`engine.tsv`: every executable, library and shader archive) |
| Program | A mod: one or more VPKs built from an addon's sources, described by a `mod.toml` (`[target]` model and skeleton, `[proven] builds`) |
| Link | Every reference a mod's compiled files make (the RERL of each resource), resolved against the mod plus the build |
| Contract | What a replaced file must keep from Valve's file at the same path: bones, attachments, hitboxes (M062), the material and texture expectations of the mesh family |
| Diagnostics | Lint rules M001 to M148, each with an in-game consequence and a fixture that triggers it |
| Re-link on a new target | `drift` and `patchday`: what changed under a mod between two builds |
| Test on hardware | The in-game harness (`ingame/`, `magician session` and `reprove`), recorded with `prove` as a proof of the bytes that were seen |

Everything that depends on a build is read from that build. A baseline is about 1 s to capture, the rig a few seconds; drift between two captured builds needs no game at all.

## Crates

Zero external crates. Each format is decoded here and checked against an independent reader (Source 2 Viewer), because a round trip through our own code proves nothing.

Dependencies run one way: `vpk`, `resource`, `expr` and `geom` depend on nothing; `mesh` on `resource`; `lint` on `vpk`, `resource`, `mesh` and `geom`; `grade` on `vpk`, `resource`, `lint` and `mesh`; `mark` on `vpk` and `resource`; the `magician` CLI on all of them.

- `vpk`: VPK v1/v2 read, single-file v2 write. Entries are sorted, so identical input gives identical bytes.
- `resource`: the compiled-resource block table, RERL (references), binary KV3 v4/v5 read and write (LZ4 and zstd blocks; the zstd decoder is RFC 8878 written here), texture headers and pixel decode.
- `mesh`: compiled model meshes (meshoptimizer vertex and index codecs v0/v1, packed vertex formats, draw calls per LOD), skeleton, hitboxes, the cloth FeModel in `PHYS` (`mesh::cloth`, the one decoder), the glb proof, and `synth.rs`, which builds every mesh fixture triangle by triangle.
- `geom`: the geometry kernel: exact predicates, BVH, topology, intersection, clipping, mass properties, an orthographic rasterizer, PNG.
- `lint`: the rules. `deep.rs` reads inside files; `mesh/` is the M1xx family (`mesh/rules.rs` holds every judgement constant); `policy.rs` the fair-play limits a run is handed; `allow.rs` the per-site allowances; `baseline.rs` the build table; `cache.rs` the findings cache; `par.rs` order-keeping parallel map.
- `grade`: a hero's footprint from the game's own data (`footprint.rs`), the rubric (`rubric.rs`, the single home of every grading number), identity (`identity.rs`), fair play (`compliance.rs`), the record and its label (`record.rs`), the policy reader (`policy.rs`), the `mod.toml` reader (`manifest.rs`), the measurements inside files (`evidence.rs`), SHA-256 and the one JSON writer.
- `expr`: material `DynamicParams` expressions, parsed and proved by interval arithmetic.
- `mark`: the maker's mark, a keyed invisible watermark in colour textures, with its own PNG, TGA, PSD and zlib codecs and BC1/BC3/BC7 encoders.
- `magician`: the CLI. `main.rs` (dispatch, lint, grade, drift), `cli.rs` (`--help`, `--version`, the options each command takes and the nearest real one, the exit codes), `paths.rs` (locations, below), `modctx.rs` (the mod of the working folder, below), `heroes.rs` (the game's hero table, read natively), `checkcmd.rs`, `doctor.rs`, `update.rs` and `updateapply.rs` (`magician update`, below), `initcmd.rs`, `newcmd.rs` (a mod's folder from nothing), `frontdoor.rs` (`session`, `reprove`, `bundle` and `source`: the Python tools run with the caller's arguments, stdio and exit code), `build.rs`, `lock.rs`, `install.rs`, `scene.rs` (scene patches), `patchday.rs` / `patchcmd.rs`, `proofs.rs` (the proof ledger), `meshcmd.rs`, `clothcmd.rs`, `markcmd.rs`, `gamefiles.rs`, `jsonout.rs` (hand-written JSON), `out.rs` (every write to stdout and stderr), `style.rs` and `progress.rs` (colour and a progress line, on a terminal only).

## Locations

Magician works against things it doesn't own: the game install, Valve's CSDK, the Source 2 Viewer CLI, and a reference folder of per-build data. None of them has a fixed home, so each resolves the same way, first answer wins: a flag, an environment variable, a key in the config file, then discovery. The table of every location, with its flag, variable, key and default on each system, is in [README.md](../README.md#where-it-finds-things), and `magician paths` prints every answer with its source. What the table leaves to the code:

- **The game** is found through Steam's `libraryfolders.vdf`, every library it lists.
- **The mods** `patchday` and `reprove` check, when nothing names them, are found by `patchday::mod_tomls_under`.
- **The toolkit folder** falls back to the checkout the program was built from (`CARGO_MANIFEST_DIR` at build time), so a build into a `CARGO_TARGET_DIR` elsewhere finds it too.
- **Wine** is `wine`, then `wine64`, on PATH.
- **The update source** defaults to `<repository>/releases/latest/download`, the `repository` of the workspace `Cargo.toml` read at build time.
- **The CSDK** has no default: the commands that need it stop with an error naming the flag, the variable and the key.

The config file is one `key = value` per line, `#` comments, the last line for a key wins. It is read on every run, so a running pipeline picks up a change at its next command.

`crates/magician/src/paths.rs` is the CLI's resolver and `ingame/gamepaths.py` the harness's, line for line the same order. They must agree: install's seat check reads the game lock the harness writes, and a disagreement would let an install swap paks under a running capture. The Python side adds keys only it uses (`blender`, `blender_45`, `cinema_venv`, and `steam` with `MAGICIAN_STEAM` for the harness's launch) and treats `<reference>/work/` as the output root for QA runs, harness baselines and films.

### The mod of the working folder

A command that is not told which mod it is for takes the nearest `mod.toml` at or above the working folder (`modctx.rs`), and from it only what it was not given; an explicit argument or flag always wins. What it used goes to stderr, one line per answer with where it came from, and `magician paths` and `magician doctor` print the same answers:

| What | From, first that holds |
|---|---|
| the mod | `--mod` (a `mod.toml` or its folder), else the nearest `mod.toml` at or above the working folder |
| its paks | `[mod] paks` (relative to the `mod.toml`), else the `pakNN_dir.vpk` beside it, else the paks the install ledger holds for its owners (what the game loads); `install` takes only the first two |
| its owners | the slug with `-` as `_`, then `[mod] owners` |
| its hero | `[mod] hero`, read against the game's own hero table (`heroes.rs`: `scripts/heroes.vdata_c` decoded natively, and the English hero names), so `lash`, `Lash`, `hero_lash`, `"Lady Geist"` or a model path all name one |
| its addon | `[mod] addon`, else the CSDK addon named by the slug with `_`; `[mod] with` for `release --with` |
| its allowances | `paths::mod_allowances`, as `grade --mod` reads them (Grading, below) |
| its scenes | `[mod] scenes`, else folders with `scene-patch.txt` at `scene/` or `package/scene/`, or one level inside them |
| from which build drift compares | the last build a recorded proof holds the mod's paks on (`proofs.tsv`), else the newest baseline older than the installed build, said so |

`modctx::fill` turns a bare verb into the command line it stands for (several, when a mod has several paks to lint or install), so every command still runs exactly as if it had been typed in full. Nothing is filled in by guessing: an owner in the ledger that merely looks like the mod's (`example_voice` beside `example-skin`) is reported by `check` and `doctor` as unclaimed, never folded in.

The first time a command needs the installed build's baseline and the reference folder has none, it captures it (with the rig sidecar) as `magician baseline` would, and says so on stderr; but only when the game is this machine's own, found through Steam or named in the config file. A game named by `--game` or `DEADLOCK_GAME` is often a drill's copy, and its build number must not seed the real reference folder.

The player-side scene installers (`tools/scene_install.ps1`, `.py`) are deliberately outside this: they ship in release bundles and find the game with `--game`, `DEADLOCK_GAME` or Steam alone.

## The pipeline

- **build**: compile only the addon's real sources with Valve's resourcecompiler (CSDK), pack only outputs that map back to a live source, lint with the addon's allowances. The compiler is the one non-deterministic, external step; everything around it is ours.
- **release**: one VPK from the addon and any `--with` addons (each compiled with its own compiler), lint, grade from the same lint run, check the mark, write `release-report.txt`, `lint.json` and `grade.json`.
- **grade**: every pak of one mod as one (the lower pak number wins a shared path), linted deep unless `--light`, judged as described in Grading, below.
- **lint**: light by default (paths, references, the model contract, fair play for particles and sounds, shared files, and the mesh rules that need no triangle: LODs, budgets, material flags); `--deep` adds the rest of the mesh family (M100 to M148), which decodes every triangle. A mod is blamed only for references it introduced. A model is measured as the game draws it by default: the meshes of its default body-group choices (`m_nDefaultMeshGroupMask`), against the default hitbox set, each hitbox as the capsule, sphere or box it is. `MAGICIAN_THREADS=N` caps the threads a lint uses (1 is sequential), for a run that shares the machine with the game.
- **install / uninstall**: lint first; refuse a slot another mod owns; back up `gameinfo.gi` per build; add the addons search path idempotently; ledger every file; refuse while `deadlock.exe` runs from the game folder being changed unless the caller holds the game lock (a running game elsewhere, the real one while a test changes a scratch copy, does not count; one whose executable path can't be read does; `tasklist` and the process's executable path on Windows; `/proc` on Linux, where the game under Proton is `deadlock.exe` or `project8` by its program, not an argument), and refuse when that can't be told, except to the lock's holder; `--ignore-game` overrides. `gameinfo.gi`'s `SearchPaths` block is read as KeyValues: the key outside comments and strings, to the brace that matches its own. The ledger is changed under its lock, and the pak, `gameinfo.gi` and the ledger are written to a temporary name and renamed into place. A row whose file is missing or holds other bytes follows its crc to the one unclaimed pak with those bytes (`install::reconcile`: Deadlock Mod Manager renumbers the folder); installing the same release again then copies nothing, an update is refused rather than loaded beside the renamed copy, and uninstall removes the renamed pak. Uninstall never removes a file whose bytes are not the ones it installed (exit 3, `--force` overrides) and never acts on a ledger row that is not a `pakNN_dir.vpk` or a hero scene map.
- **scene** (`scene.rs`): a hero-page scene is a map VPK, `maps/ui/hero_prefabs/<hero>.vpk`, of which most files are Valve's compiled map byte for byte. A *scene patch* is the answer to shipping one without Valve's bytes: a folder with `scene-patch.txt` and `files/`. The manifest is tab-separated, one fact per line (`#` comments): `magician-scene-patch<TAB>1`, `map`, `mod` (the ledger owner), `built_for` (the build, informational), `result` (the author's scene CRC: `compose` and `install` refuse a scene that does not come out as it, exit 3, `--force` writes it anyway), and one row per file of the scene, which is exactly `keep` + `replace` + `add`:
  - `keep path valve_crc size`: Valve's file, kept; the player's copy must match.
  - `replace path valve_crc our_crc size`: our file (in `files/`) replaces Valve's, and the Valve file we replaced must match too, so a changed entity lump is caught.
  - `add path our_crc size`: ours, new to the map; refused if Valve's map now has a file there.

  `make` splits a built scene against the stock map (identical CRC and size is `keep`, so no Valve byte is ever written). `assemble` reads the player's stock map from `game/citadel/maps/...`, checks every Valve file by directory CRC and again by hashing its bytes, checks our files against the manifest, and returns the scene's file list or one refusal listing what differs; `vpk::write` then packs it (sorted, so identical inputs give identical bytes, and the scene an author proved is reproduced exactly). Paths in a patch are validated (lowercase, `/`, no `..`, only under the hero's own `maps/ui/hero_prefabs/<hero>` folder) because they become file reads. `install` hands the composed file to `install::install_vpk` unchanged (seat check, slot and ledger, `gameinfo.gi` backup). The game is found as every command finds it (Locations, above). A game update that touches the map makes the check fail, which is the point: the patch is re-made against the new build with `scene make`. `tools/bundle.py` carries a patch (`scenes` in `bundle.json`) with the standalone installers `install-scene.ps1` and `install-scene.py`.
- **check** (`checkcmd.rs`): one mod's verdict on the installed build: its paks graded together (the grade's lint, deep unless `--light`, is the lint; without the Source 2 Viewer CLI each pak is linted instead and the grade step says why), its proof (the builds a recorded proof holds the bytes judged on: its own paks, else every file installed for it, scenes included; a file that changed since the proof is named), drift from the last of those, each scene patch assembled against the stock map. Exit 1 broken, 4 re-prove (these bytes not proven on the installed build, whether or not anything changed under it), 0 clean; `--json` is `magician.check/1` with the grade record inside. It runs the other commands' work in-process with their reports muted (`QUIET`), so it reads their results, never their text.
- **update** (`update.rs`, `updateapply.rs`): finding out whether there is a newer Magician, and installing it, only when asked. It is the one place Magician touches the network (with `doctor --updates`), and nothing else checks, phones home or nags: a grade is worth something only while the judge stays the same, and Magician writes into a game install.
  - **A release** is one asset per platform (`magician-windows-x64.zip`, `magician-linux-x64.tar.gz`; `update` picks the one for the platform it runs on, and a source with none is refused as "no build for <platform>"), `SHA256SUMS` over every asset and `VERSION`, in the flat `key = value` form of the config file: `version`, `commit`, `date` (the commit's), `rubric` (`grade::rubric::RULES_VERSION`), `policy` (the fingerprint of the built-in policy), `lint_rules` and `lint_fingerprint` (the count, and a SHA-256 over every rule's code, name and severity). `update --describe` prints the running build's, and `tools/make-release.ps1` writes `VERSION` from it, so it is never typed.
  - **The source** is a folder (copied) or an https URL (`curl`, bounded to 10 s or `MAGICIAN_UPDATE_TIMEOUT`, a stalled download ended after that long without progress, a `magician/<version>` agent and nothing else; a plain `http` address is refused except on this machine, which is how the tests serve one).
  - **`--check`** compares version first, then commit: two commits of one version are ordered by their dates, and on one day, or with no date, a different commit counts as an update. It also compares the judgement fingerprints and names what differs (`judgement.changed`, `differences`, `rerun`). Exit 0 current or ahead, 5 behind, 3 unknown; `magician.update/1`.
  - **Applying to a release install** (no `.git`): check the asset's SHA-256 against `SHA256SUMS`, unpack with `tar -xf` beside the toolkit, run the unpacked `--version` and require it to say what `VERSION` says, move each entry of the toolkit into `.magician-previous.partial` and rename the new one in (a failed step puts every entry back, so a toolkit is either the old one or the new one), run the installed `--version` again, then keep the old files as `.magician-previous` until the next update (Windows cannot delete the running `magician.exe`).
  - **Applying to a git checkout** follows its branch: clean tracked files, an upstream, a fetch, `merge --ff-only`, `cargo build --release`, and on any failure `reset --hard` to where it was and the program put back. The one place the platforms differ is `program_locked_while_running`: Windows will not overwrite a running exe, so a checkout's build output is renamed aside first.

  Both refuse while the game lock names a holder. Exit 3 means nothing changed, 1 means the swap began and was rolled back. `crates/magician/tests/update.rs` holds all of it on scratch toolkits, including a swap made to fail for real; a crash halfway through a swap is not covered (the `.partial` folder it leaves makes the next update refuse and say where the old files are).
- **doctor** (`doctor.rs`): read-only; one row per dependency (`ok`, `todo`, `skip`, `FAIL`) with its fix; exit 1 when one fails; `magician.doctor/1`.
- **drift / patchday**: compare two baselines and two rig sidecars under each installed pak; check the model contract against Valve's current models; read each `mod.toml`; one verdict. `patchday` compares each mod from the last build a proof holds its installed bytes on (the ledger owner being the slug or one of `[mod] owners`), so a mod whose installed files are proven on the installed build is current; per era it also says whether the engine changed (`engine.tsv`: size and sha256 of every executable, library and shader archive, and `gameinfo.gi` as shipped, or not known), which informs how hard to look and never the verdict; a mod whose bytes no proof holds, and an owner no manifest claims, are compared from the previous baseline, said so.
- **prove** (`patchcmd.rs`, `proofs.rs`): after the in-game pass was looked at, a proof of the bytes into `proofs.tsv`: every file the install ledger holds for the mod's owners, each read and checked against the ledger's crc (refused, exit 3, nothing written, when one is missing or replaced, or none is installed), or the files `--pak` names; the build (installed, or `--build`), the date (`--date`), the evidence (`--evidence DIR`: its path and its `index.md`'s sha256). The build also goes into `[proven] builds`. Proven, everywhere, is one question: does a complete recorded proof of that build hold the sha256 of every file judged. A build `[proven] builds` lists that no proof binds to these bytes is a legacy claim, reported as "claimed for other bytes or never recorded" and never removed from the `mod.toml`. `release` reads the ledger for the pak it wrote and says whether those bytes are proven (only the same bytes again keep a proof; a rebuilt pak inherits none).

## Determinism and speed

Parallel work goes through `lint::par::map`, which keeps input order (and uses at most 12 threads, `MAGICIAN_THREADS=N` fewer); anything that sums floats folds in input order afterwards. So a threaded run is byte-identical to a sequential one: the mesh census of ours and Valve's model, the models of one mod, the census's own lanes (triangle pairs, then the contact graph that reads them; boundary-loop probes, then the hitbox envelope; texture decodes; the per-surface measures) and the heavy loops inside them all run side by side and give the same findings. A new mesh pass reads the census read-only and returns its result, and a model rule reads other files only through its `read_ours` and `read_valve` closures, or the cache cannot see what it depended on.

**The findings cache** (`lint/src/cache.rs`) keeps one entry per model and depth: what the model rules said about it, not the census behind it (hundreds of megabytes of geometry), because the findings are all a later run needs. The key is the model's bytes, its path, the depth, whether Valve has a file there, the game's identity (the build string and the size and time of both `pak01_dir.vpk`), the fair-play limits in force, and a fingerprint of the rule code: `lint/build.rs` hashes the sources of `lint`, `mesh`, `geom`, `resource` and `vpk` at build time, so any edit to a rule or a decoder retires every entry without anyone bumping a version. Every file a judgement read (a material, a texture) is recorded with the CRC and size the mod had, and an entry is served only while the mod still has exactly that. So a hit is always what a fresh run would say. Entries are small text files under `model/` in the cache folder (`MAGICIAN_CACHE` moves it; at most 400, the oldest quarter dropped past that); a missing, half-written or unreadable entry is a miss, never an error. `magician cache stats` and `cache clear` manage it, and `--no-cache` or `MAGICIAN_NO_CACHE=1` skips it for a run. Per-build Valve data (`particle_classes.tsv`, `users.tsv`, the baseline) lives in the reference folder instead.

**`build` skips the compiler when nothing changed.** resourcecompiler takes about 10 s to start and say "up to date", so after a good compile `build` writes `magician_build.stamp`: a hash of every content file's path, size and time, the compiler binary's identity, and the same for the outputs. While both match, the compiler is not started; `--force-compile` runs it anyway, and a failed compile removes the stamp.

Deep lint of a hero model is about 8 s cold and 1 s cached; a whole patch-day check is 2 to 15 s, depending on whether the disk cache is warm. `--timings` on `lint`, `build` and `release` prints where the time went. Whole-game scans read VPK entries in (archive, offset) order, because on a spinning disk directory order is about 18 times slower.

## Interfaces for automation

- **Exit codes**: 0 clean; 1 broken; 2 usage error; 3 refused on purpose; 4 re-prove; 5 an update is available (`update --check` only) (reason for 1 to 3 on stderr after `magician:`, and with `--json` as the one document, schema `magician.error/1`). One enum, `cli::Stop`, carries the reason a command stopped, so a refusal can't be mistaken for a typo. Listed in `magician --help`.
- **Output** goes through `out.rs`: a reader that stops reading (`| head`) closes the stream for the rest of the run, which goes on and exits with its own code instead of panicking. Colour (`style.rs`) and the progress line (`progress.rs`, after 1.5 s) appear only on a terminal, so piped bytes never change, and every word reads without them: a grade's `broken` is red (and red means only that), `NSFR` pink, `FP?`, `stale(N)` and `unproven` orange, a fair-play pass green. Tools Magician runs keep off its stdout (Source 2 Viewer's output is closed).
- **No command**: `magician` alone prints a short orientation (the game and build, the mod here, the next commands) on stderr and exits 2, so an empty command in a script never reads as success.
- **`--help` and `--version`** are answered before anything else runs. Options are checked against the usage text, so a typo is exit 2 (naming the nearest option of that command, or the nearest command), and an option that takes no value never swallows the argument after it. An option that takes a value must have one that is not the next option, and only those the usage marks repeatable (`[--allow FILE]...`) may be given twice (`cli::check_values`).
- **JSON**: `--json` on `check`, `doctor`, `lint`, `grade`, `drift`, `patchday`, `prove`, `release`, `rules` and `update` (and `reprove`, through the front door) prints one document with a `schema` string and turns the human text off; `lint --json-out`, `mesh --json-out` and `grade --record-out` write a file, and a file that could not be written stops the command (exit 2). One writer (`grade::json`, no serialisation crate), numbers printed the same way every time.
- **MCP**: `mcp/server.py`, Python stdlib only, runs the release binary as a subprocess with timeouts and returns JSON: the commands' own documents for those with `--json`, a small parse of the tab-separated or text output for the rest (`cloth`, `refs`, `ls`, `dump`, `verify`, `install --status`, `policy`). It has no install, uninstall or launch tool by design.
- **Locks for shared resources**: the per-addon build lock and the game lock (`ingame/gamelock.py`, holder named by `MAGICIAN_GAME_HOLDER`) let several pipelines or agents share one machine and one game.

## Grading

A grade is a record of separate properties (schema `magician.grade/3`, `record.rs`) and a label projected from it:

```text
<Kind> (<groups>)[ · broken][ · NSFR | · FP?][ · stale(<last proven build>) | · unproven]
not graded (<kind>)[ · broken][ · NSFR | · FP?][ · stale(<build>) | · unproven]
```

`<groups>` names look, effects and sound in that order: the group when covered, `some <group>` when begun, nothing while Valve's (`nothing measured` when no group has anything of the mod's own).

- **Identity** (`identity.rs`) decides the archetype from signals, stored as data: `head_replaced` (our head-weighted vertices against Valve's head, `evidence::compare_models`), `renamed` (the mod's localisation names the hero anew, or a replaced name logo for a `mod.toml` name that does not keep the hero's), `new_hero_art` (the portrait and card art), `voice_identity` (declared in `mod.toml`, half a signal). Two make a new character, which needs its model replaced. A replaced model that keeps Valve's mesh, or Valve's model with new materials, is a variant; no model is a kit; a mod that touches nothing of the hero is not graded.

  | Identity | Rubric | Word |
  |---|---|---|
  | new character | character | Echo |
  | same character | character | Costume |
  | same model | variant | Variant |
  | no model | kit | Kit |
  | not a hero mod | none | not graded (map, HUD, music, prop, effects or sound mod) |

- **Description** (`rubric.rs`): eight criteria, each in one group: look (model, materials, UI art, scenes), effects (ability VFX, animation), sound (kit sound, voice). Each archetype has required criteria and applicable ones that count once touched (a character counts its voice once it treats one; a variant adds VFX, animation, sound and voice once it touches them; a kit counts only what it touches), and weights that say how much each counts within its group. A group's coverage is the weighted mean of its counted criteria; at `groups.covered` (0.8) it is named, above nothing and at `groups.touched` (0) it is `some`, else left out. Coverage is per group of files (an ability, a moment), and a band with fewer files in the hero's footprint than its target is full at what the hero has. Each group's line says what was counted: a covered criterion by name, an untouched one as Valve's, a partial one by its count (`UI art 11 of 13`, `VFX for 4 of 4 abilities (2 in part) and the weapon`). Files byte-identical to Valve's at the same path count for nothing.
- **broken** is `LintFacts::broken`: a lint error that is not fair play, allowed or not. `check` reads the same function for its verdict. Shipping a skeleton, graph or data file (an M070 error at a game path, so broken too) and unallowed M061 dropped dependencies are notes in the report and in `description.notes`.
- **Compliance** (`compliance.rs`): pass, fail (NSFR) or unknown (FP?). The fair-play rules are M062 (hitboxes only), M063, M081, M082, M124, M129, M130, M131, M140; each is never allowable (a hidden cue, a smaller silhouette, M129's egregious hitbox overflow), advisory (reported, never a violation: M081, M130), or bounded (an allowance holds within the limit the rule's own measure is checked against: M140's worst point and visible share, up to the M129 line, read back from its message by `mesh::rules::envelope_measures`). A light lint over a model, or any M144, makes the rules it names unknown. Fair-play findings and M144 never make a mod broken.
- **Freshness** is asked of the paks graded: the builds a recorded proof (`proofs.tsv` beside the `--mod`) holds every one of them on, against the target build (installed, or `--target`). Builds `[proven] builds` lists for other bytes or without a record are carried in the record as `unbound` and in the blocker's words, and count for nothing.
- **Rights** is a person's verdict in `mod.toml` (`[rights] state`: unreviewed, cleared, denied).
- **Enforcement**: fair play and rights are lenient by default and enforced with one switch each in the policy. `fair_play.enforce = false` reports every fair-play finding and M144 as a warning (`compliance::severity`, applied to the lint run that `lint`, `build`, `release`, `install`, `grade` and `mesh` act on), so nothing stops on them alone; `true` makes every one that can fail fair play or leave it unknown (all but the advisory rules) an error. `rights.enforce` decides whether `unreviewed` blocks the gate. The label and the record say the same either way; the record's policy object carries both switches.
- **Release gate**: blockers are lint errors that are not fair play, files byte-identical to Valve's, not proven on the target, and rights denied; fair play unknown, NSFR and unreviewed rights are blockers when enforced and warnings when not.
- **Allowances**: every `--allow` and `--addon-root` file; with neither, `grade --mod` reads the mod's own (`paths::mod_allowances`: `addon/magician.allow` and `magician.allow` beside the `mod.toml`, then the CSDK addon of its slug and of each `[mod] owners` entry, each file once). The record's `allowance_files` names each file read with its SHA-256 and where it was found, or says none was.

The record also carries the toolchain and commit, the build, SHA-256 fingerprints of the baseline (its canonical text and the rig sidecar), of every pak and of the policy, the kind, every group with its state, coverage and what was counted, every criterion with its measured coverage, the notes, every signal with its evidence, check run or not run, violation, allowance with value and limit, and advisory, and the next steps. Its fields are in a fixed order and its numbers print one way, so the same inputs give the same bytes.

Decisions taken in building it, where the design left them open:

- A replaced name logo is a rename only when the mod's name (`[identity] name`, else `[mod] name`) does not keep the hero's: Maid Lash ships a new `lash` logo and is still Lash. A localisation that renames the hero counts on its own.
- `head_replaced` compares our LOD0 vertices weighted most to `head` or a bone below it with Valve's, within 0.1 units; under half on Valve's head is a new head (a new head 16%, Maid Lash 78%). The same comparison over the whole mesh tells a variant (98% or more on Valve's) from a costume.
- A new character needs its model replaced: a rename and new art on Valve's model are a kit, not a new body.
- M081 (brighter particles) and M130 (the wide envelope below the taste tier) are advisory: a brighter cue is not a hidden one, and M130 fires on both reference skins' cloth. M062 counts as fair play only for hitboxes; a lost bone or attachment is the mod not working: broken.
- A voice counts once the mod treats it, for every archetype: most skins never touch the voice, and `sound` means the kit sound is the mod's own. An untouched voice is still in the sound line, as `Valve's voice`; so is every other criterion in scope that the mod has not touched.
- The default lines were set on real mods: every group of the reference mods that a person would call the mod's own measures 0.85 or more (the lowest, a kit sound with every ability, the weapon and movement but not melee), and 0.8 sits under that. `groups.touched` is 0, so `some` means begun and left out means Valve's.
- The label carries no letter and the record no overall score: the criteria's coverage is there for anyone who wants to weigh it.
- A mod with no proven build on record reads `unproven` in the label, beside `stale(N)` for one proven on an older build.
- `grade` lints deep by default, since fair play needs the mesh rules; `--light` is the quick look and reads `FP?` for a model.
- Files byte-identical to Valve's at the same path count for nothing in the description and block the gate.
- The record's paths are file names, not absolute paths, so the same paks graded on two machines give the same bytes; a grade on the same inputs is byte-for-byte reproducible (a test holds it on Maid Lash).
- `release` does not exit on the gate: a fresh release is never proven yet, and its rights are a person's call. `grade --gate` is the check a publishing step runs.

**Policy** (`grade::policy`, `lint::policy`): every judgement number is a key of a plain-text policy file, defaulting to its constant. The keys are listed with their ranges by `magician policy`; a file is read strictly (unknown section or key, wrong kind of value, out of range, set twice, a touched line at or above the covered one, tiers out of order, the retired `[letters]`: a usage error with the line). The fingerprint is SHA-256 of every effective `key = value` line, so a file that spells out the defaults has the default fingerprint.

## Mesh rules

`crates/mesh` decodes a compiled model down to every triangle, and `lint/src/mesh/` judges it in three strata: the census measures (`census.rs`), the rules judge ours against Valve's census of the model at the same path (`rules.rs`, which holds every threshold), and the findings are emitted. The geometry kernel, `crates/geom`, is a port of the scene3d compiler's math to Rust: exact `orient2d` and `orient3d` over the dyadic rationals floats are, exact topology, triangulation, clipping, mass properties, a BVH and a rasterizer. What the port left out are scene3d's authoring operators and its own deliverables, which a compiled model has no use for.

- **Exact, not tolerant.** Shells are vertices welded by exact position: the compiler splits vertices at every UV and normal seam, and a tolerance weld would hide real cracks. Compiled positions are float32, so at the 105 units a hero reaches one step is 7.6e-6 units; a twin card's two faces 0.0024 to 0.008 units apart are hundreds of steps, so compiling cannot make them cross, and twins are judged by the depth precision instead (0.3 mm, the same bound as z-fighting).
- **Valve's model is the design.** What Valve's model shares at the same place (an opening of about the same size, crossings of Valve's own materials, Valve's unchanged pieces) is not a finding, and budgets are Valve's model rather than a table of roles: Valve's Lash is 59,378 unique vertices, not the 98,077 a sum over draw calls gives. The hero's skin is the material Valve names `*_body`, `*_head`, `*_face` or `*skin*`, and the contact closure starts from it, not from the largest shell, which is often a garment.
- **Views a player can reach.** An opening is probed with rays from a cone of outside viewers, and a cut in the skin from around the kept skin's outward normal, never along the cap's own normal, which looks up inside the chest. That rule came from a scar: a probe along the cap read a closed inner hull sunk 8 mm as 76 units of unbacked edge, and twin-backed cards read as see-through because a pinched outline (a vertex visited twice) fell back to a fan that spanned air. Pinched loops are split into simple rings, a ring that folds in every projection is reported as M100 rather than capped, and opposite-facing rims are a double-layer card, not a crack (M125).
- **What the geometry does not prove.** Everything is measured at bind pose: a defect that only shows in motion is caught by its static cause (an unbacked cut, a piece skinned off its substrate, weights to distant bones), not by posing. Cloth is judged from the compiled FeModel as damped oscillators (M141), compared with Valve's group at the same place, never simulated. The probe views are orthographic, 22 directions; the game's camera is perspective. Animation clips are not decoded, so the contract (M062) covers bones, attachments and hitboxes, not anim events.
- **Tables that come from Valve's files.** M143's table of shader combos that break `pbr.vfx` is encoded in `lint/src/pbrcombo.rs` from the shader's `pbr_pc_50_features.vcs` on 6864, read with Source 2 Viewer, not parsed at lint time: re-read it when a build changes the shader. M141's line is relative because Valve's own cloth rings: 52 of its 339 groups on 6864 are past four swing cycles at 1 Hz or more.

The decode is proven, not trusted: `magician mesh ... --glb <Source 2 Viewer export>` matches LOD0 of Valve's Lash (2 meshes, 4 draws, 59,390 vertices, 125,579 triangles) and of Maid Lash (13 draws, 100,271 vertices, 159,884 triangles): identical triangles, positions within 6e-6 units, normals within 1.8e-7, UVs, weights and bone names exact. Texture pixels are bit-exact against Source 2 Viewer's PNGs over 25 million pixels.

## The maker's mark

`crates/mark` puts an invisible authorship watermark in a mod's colour textures (`magician sign`) and finds it in a compiled pak (`magician verify`). The key is the mod's author (`--key`, else `[mark] key` or `[mod] author` in the `mod.toml`); there is no built-in key. It is public on purpose: the mark proves authorship by being there and by its payload (the mod and the signing date), which only that key decodes, not by secrecy. `MAGICIAN_MARK_SECRET`, from the environment only, adds a second pattern for a claim nobody else can reproduce.

- **Where it lives.** A texture is a grid of cells that, on a power-of-two texture, are the 4x4 blocks of BC1, BC3 and BC7, and the mark is a small per-block offset of luminance (0.9 grey levels RMS, the same on R, G and B), what block compression keeps best. Cells are in normalised coordinates, so the grid survives size clamps and power-of-two resizes. The full scheme is at the top of `crates/mark/src/scheme.rs`.
- **Why it can be trusted.** Detection needs only the key and the compiled pixels. For an unmarked texture the weights depend on the image alone and the chips are fair independent signs, so the chance of a false detection is bounded by exp(-z²/2) with no model of the image, and the bound stays exact pooled over a pack. On Valve's whole pack (7,535 colour textures on 6864) nothing is detected: the largest z is 3.89.
- **What it must not touch.** Only cells fully opaque and 32 pixels clear of any alpha edge are marked, and alpha is never written, because the compiler packs translucency or metalness into a colour map's alpha ([reference/engine.md](reference/engine.md), Textures) and a BC block at mip k reads 4·2^k source pixels. With an 8-pixel margin a lace map lost texels at mips 3 and 6 and packed metalness moved by 20 levels; at 32 the coverage is bit-identical at every mip. Not marked, and listed with the reason in `magician.signed`: anything not colour, light cookies, sprite-sheet frames (packing moves them off the grid), sources also used as a non-colour input, and sources with under 2,048 markable cells or a projected z under 8 after the format they compile to.
- **A step after the generators.** Texture sources are regenerated by a mod's own scripts, which overwrite them, so the mark is never written by a generator: `magician sign <addon>` runs after any of them and before `build` or `release`. `build` never writes sources; it and `release` check `magician.signed`, name a source whose hash changed since signing, and verify the packaged textures (`signed: N/M`).

## Outside the Rust workspace

- `ingame/`: Python stdlib (3.11 or newer for the session driver and `reprove`, which read `mod.toml` with `tomllib`); drives the retail game as a player would, with hardware keys and a capture of its window. Everything it asks of the system goes through `gameos.py`: processes from tasklist and kernel32 on Windows and `/proc` on Linux, and the display through user32 and gdi32 (SendInput scancodes, PrintWindow) or X11 (libX11 and libXtst through `ctypes`: XTest keys and mouse, XGetImage). A machine without a display backend refuses before the seat is taken. `magician session` and `magician reprove` run `mod_session.py` and `reprove.py`; the PowerShell `launch.ps1` and `stop_game.ps1` are thin callers of `launch.py` and `stop_game.py`.
- `qa/`, `harness/`: Blender 5.2 headless plus Python; Source 2 Viewer exports the glb files they read. `qa/run_qa.py` (with `qa/run_qa.ps1` as its PowerShell spelling) runs every visual check on a compiled character mod against Valve's model into a dated report under `<reference>/work/<mod>/qa/`, with exports cached by content hash. The mod's model and its clips are packed into one VPK for the export, so what is checked is our mesh on Valve's skeleton playing our clips (Valve's for the rest), and every check runs on both models, so Valve's own counts sit beside ours. Findings are triaged as `valve-own` (Valve's model shows the same thing there), `clip` (only on a replaced clip, not on our mesh with Valve's clip) or `mesh`, and weighed by the area a camera sees. A hero's profile is `qa/heroes/<hero>.json` (`haze.json` is the example; a mod keeps its own). It does not prove the cloth solver, LOD switching or shaders (Blender's renderers stand in for the game's): only the game shows those.
- `mcp/`: Python stdlib.
- `tools/`: `bundle.py` (player release bundles with `mod-interchange.json`; Pillow for previews) and `source.py` (a static Deadlock Mod Manager mod source from bundles), behind `magician bundle` and `magician source`; `scene_lump.py` (re-dress a UI scene map's entity lump through `magician dump` and back), `scene_install.ps1` and `scene_install.py` (the player-side scene installers bundles carry: Windows PowerShell 5.1 or Python 3 stdlib, no Magician), `s2v_mcp.py` (the Source 2 Viewer MCP server: started on Windows, where its GUI runs, and spoken to from anywhere), `rip_heroes.py` (hero models to glb for reference work, keyed by build, never committed); each keeps a `.ps1` caller.
- `cinema/`: the dev-only film kit, with its own README.

## Verification

`cargo test --workspace` runs on synthetic fixtures only and needs no game. Every lint rule has a fixture that breaks it, enforced by `every_rule_has_a_fixture`. Decoders are pinned against Source 2 Viewer's output by golden values. What only the game can show is proved in the game, and what only a picture can show is looked at.

Every reader of bytes or text someone else made is fuzzed (`crates/fuzz`, a dev-dependency with no dependencies of its own): VPK trees and entries, the resource block table and RERL, binary KV3 v4 and v5 with LZ4 and zstd, the LZ4 and zstd decoders alone, texture headers and pixels, KV3 text, compiled models with every LOD's surfaces, both meshoptimizer codecs, cloth, glb and its JSON, a whole lint (light and deep) over one hostile file, `magician.allow`, findings files, baselines, the policy, `mod.toml`, DynamicParams expressions, the mark's PNG, TGA, PSD and inflate, and the CLI's scene patches, ledger, locks, `gameinfo.gi`, `prove`'s rewrite, rig sidecars, `magician.exclude`, the config file and Steam's library list. A case must return within 10 s without panicking or asking for one allocation over 256 MiB; cases are deterministic, so a failure names the one that reproduces it, and the inputs that found bugs are kept beside each target and replayed first. Where a format has both directions the round trip is held too (VPK, KV3, meshoptimizer, deflate and PNG, baselines, findings files, rig sidecars, scene patches, the policy). The workspace builds with overflow checks in every profile, release included, clippy's correctness and suspicious groups as errors, and no `unwrap`, `expect` or `str` slicing in the readers; CONTRIBUTING.md has the commands.
